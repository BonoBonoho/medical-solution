# 09. PC 사용 통제

> ⚖️ **이 기능은 법적·노무적 리스크가 가장 큰 영역입니다.** 근로자 모니터링은 개인정보보호법, 통신비밀보호법, 근로기준법이 얽혀 있고, 절차를 지키지 않으면 회사가 처벌받습니다. **반드시 법무·노무 검토를 거쳐야 하며, 이 문서는 설계 참고용입니다.**

---

## 1. 요구의 실체와 위험

### 1.1 고객이 원하는 것

원무·행정·검사실·콜센터 등 PC 상주 직군에서 근무시간 중 넷플릭스·유튜브·쇼핑·게임 사용이 문제가 된다는 요구는 실재합니다. 특히 다음 상황에서 강하게 제기됩니다.

- 야간 당직 근무자의 장시간 스트리밍
- 대기 시간이 긴 부서에서의 상시 사용
- 특정 인원에 대한 민원 발생 후 "확인이 필요하다"는 요구

### 1.2 잘못 만들면 생기는 일

| 위험 | 결과 |
|---|---|
| 개인 브라우징 이력을 수집·보관 | 개인정보보호법 위반 소지, 유출 시 대형 사고 |
| 근로자 동의·고지 없이 도입 | 노무 분쟁, 부당노동행위 논란 |
| 휴게시간에도 차단 | 휴게시간은 근로자가 자유롭게 이용할 수 있어야 함 (근기법 §54②) |
| 개인별 상세 사용 내역을 관리자에게 노출 | 감시 도구화, 직원 신뢰 붕괴 |
| 의료진의 진료 관련 사이트 차단 | 환자 안전 문제 |

**마지막 항목이 가장 위험합니다.** 의사가 약물 상호작용을 확인하려는데 차단되면 그건 제품 문제가 아니라 의료사고입니다.

### 1.3 우리의 입장

이 기능은 **"업무 집중 지원 도구"이지 "감시 도구"가 아닙니다.** 이 구분을 제품 설계로 강제합니다.

## 2. 절대 원칙 (제품 헌법)

이 원칙들은 우선순위 조정 대상이 아니라 **변경 불가한 제약**입니다.

| # | 원칙 | 구현 |
|---|---|---|
| 1 | **전체 URL·검색어·페이지 내용을 저장하지 않는다** | 확장에서 도메인으로 잘라 전송. 서버 스키마에 URL 컬럼 자체가 없음 ([04 §9](04-data-model.md#9-pc-사용-통제)) |
| 2 | **화면 캡처·키로깅을 하지 않는다** | 영구 비목표. 기능 요청이 와도 거부 |
| 3 | **휴게시간·퇴근 후에는 정책이 해제된다** | 근태 상태와 연동, 기본값 ON |
| 4 | **차단 시 이유를 항상 표시한다** | 차단 페이지에 정책명·수집 항목·이의 제기 경로 표시 |
| 5 | **의료·진료 관련 도메인은 기본 허용 목록에 있다** | 시스템 기본 화이트리스트 제공, 삭제 불가 |
| 6 | **개인별 상세 리포트는 기본 비공개** | 부서 집계만 기본 노출. 개인별 조회는 별도 권한 + 사유 입력 + 감사 로그 |
| 7 | **직원이 자신의 수집 내역을 열람할 수 있다** | 앱/웹에 "내 사용 기록" 화면 제공 |
| 8 | **도입 시 동의·고지 절차를 강제한다** | 설정 마법사에서 절차 완료 없이 활성화 불가 |

원칙 8이 제품적으로 중요합니다. 고객이 절차를 건너뛰면 **고객이 위법 상태**가 되고, 결국 우리 제품의 문제로 돌아옵니다.

## 3. 아키텍처

### 3.1 채택: 브라우저 확장 + 정책 서버

```
┌─────────────────────────────────────────────────────┐
│  직원 PC                                             │
│  ┌───────────────────────────────────────────────┐  │
│  │ Chrome / Edge (엔터프라이즈 정책으로 강제 설치)│  │
│  │  ┌─────────────────────────────────────────┐  │  │
│  │  │ MediWork 확장 (MV3)                     │  │  │
│  │  │  ├ Service Worker                       │  │  │
│  │  │  │   · 정책 폴링 (5분)                  │  │  │
│  │  │  │   · declarativeNetRequest 규칙 갱신  │  │  │
│  │  │  │   · 사용 집계 (도메인+카테고리)      │  │  │
│  │  │  └ 차단 페이지 (이유·이의제기)          │  │  │
│  │  └─────────────────────────────────────────┘  │  │
│  └───────────────────────────────────────────────┘  │
└──────────────────────┬──────────────────────────────┘
                       │ HTTPS
                       ▼
              GET  /pc-control/policy   (정책 조회)
              POST /pc-control/usage    (집계 보고)
```

**Manifest V3의 `declarativeNetRequest`를 쓰는 이유**: 확장이 URL을 읽지 않고 브라우저가 규칙만으로 차단합니다. `webRequest` 차단 API처럼 모든 요청 URL이 확장 코드로 흘러들어오지 않으므로, **원칙 1(URL 미수집)을 기술적으로 보장**할 수 있습니다.

### 3.2 왜 네이티브 에이전트를 기본으로 하지 않는가

| 항목 | 브라우저 확장 | 네이티브 에이전트 |
|---|---|---|
| 설치 난이도 | 엔터프라이즈 정책으로 자동 배포 | MSI 배포, 관리자 권한, 백신 오탐 |
| 우회 난이도 | 다른 브라우저 설치로 우회 가능 | 우회 어려움 |
| 개발·유지비 | 낮음 | 높음 (OS 업데이트마다 대응) |
| 법적 리스크 | 낮음 (브라우저 범위 한정) | 높음 (OS 전체 감시 인상) |
| 직원 수용도 | 상대적으로 높음 | 낮음 |

**우회 가능성을 감수합니다.** 완벽한 차단을 목표로 하면 감시 도구가 되고, 그러면 원칙 1~8을 지킬 수 없습니다. 이 기능의 목표는 "물리적 차단"이 아니라 **"업무 외 사용에 마찰을 주는 것"** 입니다.

네이티브 에이전트는 **명시적으로 요구하는 고객에게만 옵션**으로 제공하고, 그 경우에도 원칙 1~8은 동일하게 적용합니다.

## 4. 정책 모델

### 4.1 정책 구조

```jsonc
{
  "name": "원무팀 근무시간 정책",
  "scope": {
    "departmentIds": ["dept-admin-001"],
    "jobFamilies": ["ADMIN"]
  },
  "applyWhen": "WORKING_HOURS",   // ALWAYS | WORKING_HOURS | SCHEDULED_HOURS
  "excludeOnBreak": true,          // 기본값 true, 해제 시 경고 표시
  "blockCategories": ["STREAMING", "GAME", "GAMBLING", "ADULT"],
  "blockedDomains": [],
  "allowedDomains": [],            // 기관 추가 허용
  "action": "BLOCK",               // BLOCK | WARN | LOG_ONLY
  "priority": 10
}
```

### 4.2 카테고리

| 카테고리 | 예시 | 기본 차단 권장 |
|---|---|---|
| `STREAMING` | 넷플릭스, 티빙, 웨이브, 유튜브 | ○ (유튜브는 논쟁적 — 아래 참고) |
| `GAME` | 게임 포털, 웹게임 | ○ |
| `GAMBLING` | 도박, 사행성 | ○ |
| `ADULT` | 성인 사이트 | ○ |
| `SHOPPING` | 쇼핑몰 | △ 기관 선택 |
| `SNS` | SNS | △ 기관 선택 |
| `NEWS` | 뉴스, 커뮤니티 | ✕ 권장 안 함 |

**유튜브 문제**: 유튜브에는 의학 교육 콘텐츠와 장비 사용법 영상이 많습니다. 일괄 차단하면 업무를 막습니다. 옵션을 제공합니다.

```
YouTube 처리
 ├─ 전체 차단
 ├─ 전체 허용
 └─ 채널/재생목록 화이트리스트 (권장)
     예: 병원 자체 교육 채널, 학회 채널
```

### 4.3 의료 기본 허용 목록 (삭제 불가)

원칙 5에 따라 시스템이 기본 제공하며 **기관이 삭제할 수 없습니다.**

```
· 건강보험심사평가원, 국민건강보험공단
· 질병관리청, 식품의약품안전처, 보건복지부
· 대한의사협회, 대한간호협회 및 각 학회
· 의약품 정보 서비스 (KIMS, 드러그인포 등)
· 의학 문헌 데이터베이스 (PubMed, UpToDate 등)
· 의료기기 제조사 기술 지원 사이트
· 기관 자체 도메인
```

**"삭제 불가"가 중요합니다.** 관리자가 실수로 지우면 진료에 지장이 생깁니다. 필요하면 개별 예외를 추가하는 방식으로만 조정합니다.

### 4.4 근무 상태 연동

```
memberState 판정 (서버가 계산)
 ├─ WORKING   : 출근 기록 있음 && 퇴근 기록 없음 && 휴게 중 아님
 ├─ BREAK     : 휴게 시작 기록 있음 && 휴게 종료 기록 없음
 └─ OFF_DUTY  : 그 외

정책 적용
 WORKING  → 정책 적용
 BREAK    → 해제 (excludeOnBreak=true 시)
 OFF_DUTY → 해제
```

**상태 판정을 서버에서 하는 이유**: 확장이 스스로 판단하면 로컬 시각 조작으로 우회할 수 있고, 무엇보다 근태 상태의 단일 진실 공급원이 서버여야 합니다.

**휴게시간 기록이 없는 기관 문제**: 많은 병원이 휴게시간을 별도 기록하지 않습니다. 이 경우 `time_windows`로 고정 휴게시간(예: 12:00~13:00)을 설정해 해제합니다. 설정이 없으면 **차단을 적용하지 않는 것이 기본값**입니다 — 휴게시간을 침해하는 것보다 낫습니다.

## 5. 브라우저 확장 구현

### 5.1 배포

```
Chrome/Edge 엔터프라이즈 정책 (그룹 정책 또는 MDM)
 ExtensionInstallForcelist = ["<extension-id>;<update-url>"]
 ExtensionSettings = { "<id>": { "installation_mode": "force_installed" } }
```

- 관리형 PC에는 자동 설치·제거 불가.
- 비관리형 PC에는 강제할 수 없습니다. 이 경우 **웹 출퇴근 시 확장 미설치 안내**를 표시하는 정도가 한계입니다.

### 5.2 정책 동기화

```javascript
// service_worker.js
const POLL_INTERVAL_MIN = 5;

chrome.alarms.create('sync-policy', { periodInMinutes: POLL_INTERVAL_MIN });

chrome.alarms.onAlarm.addListener(async (alarm) => {
  if (alarm.name !== 'sync-policy') return;
  await syncPolicy();
});

async function syncPolicy() {
  const res = await fetch(`${API}/pc-control/policy`, {
    headers: { Authorization: `Bearer ${await getToken()}` },
  });
  if (!res.ok) return;                    // 실패 시 기존 정책 유지
  const { data } = await res.json();

  await chrome.storage.local.set({ policy: data });
  await applyRules(data);
}

async function applyRules(policy) {
  const existing = await chrome.declarativeNetRequest.getDynamicRules();
  const removeRuleIds = existing.map(r => r.id);

  if (policy.action === 'LOG_ONLY' || policy.memberState !== 'WORKING') {
    await chrome.declarativeNetRequest.updateDynamicRules({ removeRuleIds });
    return;                               // 차단 규칙 전부 해제
  }

  const addRules = buildRules(policy);    // allow 규칙 우선순위를 높게
  await chrome.declarativeNetRequest.updateDynamicRules({ removeRuleIds, addRules });
}
```

**정책 조회 실패 시 기존 정책을 유지**합니다. 네트워크 장애로 차단이 풀리거나(통제 무력화) 갑자기 모든 게 막히는(업무 마비) 것을 둘 다 피합니다.

**허용 규칙의 우선순위를 차단 규칙보다 높게** 설정합니다. 의료 화이트리스트가 카테고리 차단에 걸리면 안 됩니다.

### 5.3 사용 집계

```javascript
// 탭 활성 시간 측정. URL이 아니라 도메인만 추출.
function toDomain(url) {
  try { return new URL(url).hostname; } catch { return null; }
}

// 5분마다 서버로 집계 전송
async function reportUsage() {
  const buckets = await chrome.storage.local.get('usageBuckets');
  const entries = Object.entries(buckets.usageBuckets ?? {}).map(
    ([key, seconds]) => {
      const [date, category, domain] = key.split('|');
      return { date, category, domain, durationSeconds: seconds };
    }
  );
  if (entries.length === 0) return;

  await fetch(`${API}/pc-control/usage`, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json',
               Authorization: `Bearer ${await getToken()}` },
    body: JSON.stringify({ policyVersion: policy.policyVersion, entries }),
  });
  await chrome.storage.local.remove('usageBuckets');
}
```

**전송 페이로드에 URL 필드가 존재하지 않습니다.** 코드 리뷰 체크리스트에 이 항목을 넣습니다.

## 6. 차단 해제 요청 흐름

```
직원: 차단 페이지에서 "허용 요청" 클릭
  │  └ 사유 입력 (예: "장비 매뉴얼 영상 확인 필요")
  ▼
관리자: 결재함에서 검토
  │  └ 승인 시 범위 선택
  │      · 이 직원만
  │      · 이 부서 전체
  │      · 전사
  │  └ 기간 선택 (1회성 / 기간 지정 / 영구)
  ▼
정책 반영 → 확장이 5분 내 자동 반영
  │
  ▼
직원에게 결과 알림
```

- **거부 시에도 사유를 남기게 합니다.** 이유 없는 거부가 반복되면 직원 불만이 쌓입니다.
- 자주 요청되는 도메인은 대시보드에 표시합니다. "이 도메인이 12건 요청되었습니다 — 화이트리스트에 추가할까요?"

## 8. PC-OFF 연동 (Could)

52시간 준수 보조를 위해, 근무 종료 시각 도래 시 안내하고 필요 시 강제 로그오프하는 기능입니다.

```
퇴근 예정 30분 전  → 알림 "30분 후 근무시간이 종료됩니다"
퇴근 예정 시각     → 알림 "근무시간이 종료되었습니다. 연장근로 신청이 필요합니다"
+30분              → (옵션) 화면 잠금 또는 강제 로그오프
```

- **연장근로 승인 시 자동 연장**되어야 합니다. 승인받고 일하는데 컴퓨터가 꺼지면 안 됩니다.
- **강제 로그오프는 네이티브 에이전트가 필요**하므로 확장만으로는 불가능합니다. 알림까지가 확장의 한계.
- ⚖️ 검토필요: 강제 로그오프는 작업 중 데이터 유실 위험이 있고, 병원 특성상 응급 상황과 충돌할 수 있습니다. **응급실·중환자실·수술실은 적용 대상에서 제외**하는 것을 기본값으로 합니다.

## 9. 도입 절차 강제 (원칙 8)

설정 마법사에서 다음을 완료하지 않으면 기능을 활성화할 수 없습니다.

```
□ 1단계 — 취업규칙 반영 확인
    "PC 사용 모니터링에 관한 사항이 취업규칙에 반영되어 있습니까?"
    → 관련 조항 텍스트 입력 또는 문서 업로드
    → ⚖️ 취업규칙 변경 시 근로자 과반수 의견 청취(불이익 변경 시 동의) 필요

□ 2단계 — 노사협의 확인
    "근로자대표 또는 노사협의회와 협의를 진행하셨습니까?"
    → 협의 일자, 참석자, 회의록 업로드

□ 3단계 — 개인정보 처리방침 반영
    → 수집 항목, 목적, 보관 기간이 처리방침에 포함되었는지 확인
    → 시스템이 표준 문구를 제공 (복사해 사용)

□ 4단계 — 직원 고지
    → 대상 직원에게 사전 고지 발송 (앱/이메일)
    → 고지 내용에 수집 항목·목적·보관기간·열람 방법 포함
    → 고지 발송 후 7일 경과해야 활성화 가능

□ 5단계 — 정책 설정 및 시범 운영
    → 최소 2주간 LOG_ONLY 모드로 운영 권장
    → 실제 차단 전에 오탐(업무 사이트 차단) 확인
```

**5단계의 시범 운영이 실무적으로 중요합니다.** 처음부터 차단하면 반드시 업무 사이트가 걸리고, 첫날 컴플레인 폭탄이 터집니다.

각 단계는 완료 여부를 기록하고, 나중에 분쟁 시 증빙으로 사용할 수 있게 보관합니다.

## 10. 기능 요청 거부 목록

고객이 요청해도 **구현하지 않는** 항목입니다. 영업 단계에서 미리 명확히 합니다.

| 요청 | 답변 |
|---|---|
| 화면 캡처 / 실시간 화면 보기 | 제공하지 않습니다. 법적 리스크와 제품 원칙에 반합니다. |
| 키보드 입력 기록 | 제공하지 않습니다. |
| 전체 URL 이력 제공 | 제공하지 않습니다. 도메인 단위까지만 가능합니다. |
| 개인 메신저 내용 확인 | 제공하지 않습니다. 통신비밀보호법 문제입니다. |
| 휴게시간에도 차단 | 기술적으로 가능하나 기본값 OFF이며, 활성화 시 법적 위험 경고를 표시합니다. |
| 직원 몰래 설치 | 제공하지 않습니다. 고지 절차(§9)를 우회할 수 없습니다. |

**"경쟁사는 해준다"는 말이 나올 수 있습니다.** 그래도 하지 않습니다. 이 기능들은 고객사를 위법 상태로 만들고, 사고가 나면 우리 제품이 원인으로 지목됩니다.
