# 02. 의료 근태 도메인 규칙

> ⚖️ **이 문서 전체가 법률 검토 대상입니다.** 아래 내용은 설계를 위한 정리이며 법률 자문이 아닙니다. 법령·고시는 개정이 잦으므로, 구현 시 **조문을 직접 확인**하고 공인노무사 검토를 거쳐야 합니다. 특히 수가 관련 기준은 보건복지부 고시로 수시 변경됩니다.

이 문서는 제품의 **규칙 엔진(Rule Engine)** 이 구현해야 할 도메인 로직을 정의합니다.

---

## 1. 설계 원칙: 규칙은 데이터다

가장 중요한 아키텍처 결정입니다.

```
❌ if (weeklyHours > 52) throw new Error('주 52시간 초과')
✅ ruleEngine.evaluate(ruleSet.for(tenant, jobFamily, effectiveDate), timesheet)
```

**이유:**
1. 법령이 개정된다. 시행일 이전 기간은 **당시 규칙으로** 재계산되어야 한다.
2. 사업장 규모(5인/50인/300인)에 따라 적용 조문이 달라진다.
3. 직군에 따라 적용 법이 다르다 (일반 근로자 vs 전공의).
4. 특례·합의 여부에 따라 같은 사업장 안에서도 규칙이 갈린다.

따라서 규칙은 **시행일(effective_from/to)을 가진 버전화된 데이터**로 저장하고, 평가 시점에 로드합니다. 상세 스키마는 [04. 데이터 모델](04-data-model.md#7-규칙-엔진) 참고.

```
RuleSet
 ├── scope: { tenant?, worksite?, jobFamily?, employmentType? }
 ├── effectiveFrom / effectiveTo
 ├── priority          (좁은 스코프가 넓은 스코프를 override)
 └── rules[]
      ├── code           예: WEEKLY_MAX_MINUTES
      ├── instanceKey?   같은 코드의 규칙을 여러 개 둘 때의 식별자
      ├── params         예: { limitMinutes: 3120 }
      ├── severity       BLOCK | WARN | INFO
      └── legalBasis     "근로기준법 제53조" (UI에 근거 표시)
```

`severity`를 규칙 데이터에 두는 이유: 같은 규칙이라도 어떤 기관은 "저장 자체를 막아달라", 어떤 기관은 "경고만 띄우고 진행"을 원합니다. 이건 정책이지 코드가 아닙니다.

`instanceKey`가 필요한 이유: 금지 패턴처럼 **한 코드에 여러 인스턴스가 필요한 규칙**이 있습니다. `E→D 금지`와 `N→E 금지`는 둘 다 `FORBIDDEN_SHIFT_PATTERN`입니다. 코드만으로 덮어쓰기를 판정하면 뒤에 온 규칙이 앞의 것을 **오류 없이 조용히 지워버립니다.** 구현 중 실제로 발생한 결함이며, 상세는 [12. 구현 노트 §2.1](12-implementation-notes.md#21-규칙-인스턴스를-코드만으로-키잉하면-규칙이-사라진다) 참고.

## 2. 근로시간 규칙 (일반 근로자)

### 2.1 기본 한도

| 규칙 코드 | 내용 | 근거(확인 필요) |
|---|---|---|
| `DAILY_STD_HOURS` | 1일 소정근로 8시간 | 근기법 §50② |
| `WEEKLY_STD_HOURS` | 1주 소정근로 40시간 | 근기법 §50① |
| `WEEKLY_OT_LIMIT` | 연장근로 1주 12시간 한도 (당사자 합의) | 근기법 §53① |
| `BREAK_TIME` | 4시간 근무 시 30분 이상, 8시간 시 1시간 이상 휴게 | 근기법 §54 |
| `WEEKLY_HOLIDAY` | 1주 평균 1회 이상 유급휴일 | 근기법 §55① |

**주의:** "주 52시간"은 40 + 12의 결과이지 독립 조문이 아닙니다. 규칙 엔진에서도 `40 + OT한도`로 계산해야 탄력근로제 등에서 올바르게 동작합니다.

### 2.2 가산수당

| 구분 | 가산율 | 비고 |
|---|---|---|
| 연장근로 | 통상임금의 50% 이상 | 근기법 §56① |
| 야간근로 (22:00~06:00) | 50% 이상 | 근기법 §56③ |
| 휴일근로 8시간 이내 | 50% 이상 | 근기법 §56② |
| 휴일근로 8시간 초과분 | 100% 이상 | 근기법 §56② |

- **중복 적용됨**: 야간에 연장근로를 하면 연장 50% + 야간 50%가 각각 가산됩니다.
- **5인 미만 사업장에는 가산수당 규정이 적용되지 않습니다.** 사업장별 상시근로자 수를 관리해야 하는 이유.
- 야간 시간대 판정은 **시프트가 자정을 넘길 때** 특히 주의. N번(예: 22:00~08:00)은 22:00~06:00의 8시간이 야간근로입니다.

### 2.3 ⭐ 근로시간 특례 (보건업)

**보건업은 근로기준법 제59조의 근로시간·휴게시간 특례 대상 업종입니다.** 이 제품의 핵심 도메인 지식 중 하나입니다.

- 사용자와 **근로자대표 간 서면 합의**가 있으면, 주 12시간을 초과하여 연장근로를 하게 하거나 휴게시간을 변경할 수 있습니다.
- 다만 2018년 개정으로, 특례 적용 시에도 **근무 종료 후 다음 근무 시작 전까지 연속 11시간 이상의 휴식시간을 부여**해야 합니다. (근기법 §59②)

**구현 요구사항:**

```
RULE: HEALTHCARE_SPECIAL_EXCEPTION
  전제: worksite.specialExceptionAgreement != null
        && agreement.isValid(date)          // 서면합의 유효기간
  효과: WEEKLY_OT_LIMIT 규칙을 비활성화
  추가: MIN_REST_BETWEEN_SHIFTS = 11시간 (severity: BLOCK)
```

- 서면합의 문서 자체를 시스템에 보관하고 유효기간을 관리해야 합니다. 합의가 만료되면 자동으로 특례가 꺼지고 52시간 규칙이 되살아나야 합니다.
- 특례를 적용해도 **가산수당은 그대로 지급**됩니다. 특례는 "시간 한도"의 예외이지 "수당"의 예외가 아닙니다.
- ⚖️ 검토필요: 서면합의의 유효 요건(근로자대표 선출 절차 포함), 특례 적용 범위.

### 2.4 시프트 간 휴식 검증

11시간 규칙은 단순 뺄셈이 아닙니다. 실제 병원에서 문제가 되는 패턴:

| 패턴 | 예시 | 간격 | 판정 |
|---|---|---|---|
| D → D | 07:00~15:00 → 다음날 07:00~15:00 | 16시간 | OK |
| E → D | 15:00~23:00 → 다음날 07:00~15:00 | 8시간 | ❌ 위반 |
| N → D | 22:00~08:00 → 같은날 15:00 시작 아님, 다음날 07:00 | 23시간 | OK |
| D → E | 07:00~15:00 → 같은날 15:00~23:00 | 0시간 | ❌ 연속근무 |
| N off 없이 N → E | 22:00~08:00 → 같은날 15:00~23:00 | 7시간 | ❌ 위반 |

**`E → D` 패턴(속칭 '이브닝 데이', 퀵 리턴)이 가장 흔한 위반이며, 간호사 피로도·이직의 주요 원인입니다.** AI 스케줄러에서 이 패턴은 하드 제약으로 금지하는 것이 기본값이어야 합니다.

계산 시 **실제 기록된 퇴근 시각** 기준으로도 재검증해야 합니다. 근무표상으로는 11시간이 확보돼도 인계가 길어져 실제 퇴근이 1시간 늦으면 위반이 됩니다.

## 3. ⭐ 전공의 수련시간 규칙

전공의는 「전공의의 수련환경 개선 및 지위 향상을 위한 법률」(전공의법)의 별도 규율을 받습니다. **일반 근로자의 52시간 규칙을 적용하면 안 됩니다.**

### 3.1 규칙 항목

| 규칙 코드 | 내용 |
|---|---|
| `RESIDENT_WEEKLY_MAX` | 주당 수련시간 상한 (4주 평균으로 산정) |
| `RESIDENT_EDU_EXTRA` | 교육적 목적의 추가 수련시간 한도 |
| `RESIDENT_CONTINUOUS_MAX` | 연속수련시간 상한 (응급상황 시 별도 한도) |
| `RESIDENT_MIN_REST_AFTER` | 연속수련 종료 후 최소 휴식시간 |
| `RESIDENT_NIGHT_DUTY_MAX` | 주당 당직 횟수 상한 |
| `RESIDENT_MONTHLY_OFF_MIN` | 월간 최소 휴일 일수 |

### 3.2 ⚠️ 파라미터 값에 대한 중요 경고

전공의법의 구체적 시간 수치는 **개정 논의가 활발한 영역**입니다. 연속수련시간 단축, 주당 수련시간 조정에 대한 법 개정과 시범사업이 진행되어 왔습니다.

**따라서 이 문서에 수치를 하드코딩하지 않습니다.** 구현 시:

1. 시행 중인 전공의법 및 시행규칙 조문을 직접 확인하여 값을 확정할 것.
2. 시범사업 참여 병원은 별도 파라미터 세트가 필요할 수 있음.
3. 값은 반드시 `RuleSet`의 `params`에 **시행일과 함께** 저장. 개정 시 새 버전 추가로 대응.

```json
{
  "code": "RESIDENT_WEEKLY_MAX",
  "params": { "limit": null, "averagingWeeks": 4, "unit": "hours" },
  "effectiveFrom": "____-__-__",
  "legalBasis": "전공의법 제7조",
  "note": "값은 시행 조문 확인 후 확정. 개정 이력 추적 필요."
}
```

### 3.3 수련시간의 특수성

- **수련시간 ≠ 근로시간.** 교육·컨퍼런스 참여가 수련시간에 포함되는지 여부가 별도 논점입니다. 시스템은 두 개념을 **분리 집계**할 수 있어야 합니다.
- 4주 평균 산정이므로, 특정 주가 초과해도 평균이 충족되면 적법할 수 있습니다. **주 단위 경보와 4주 평균 경보를 모두 제공**해야 합니다.
- 당직 후 익일 정규 근무(속칭 '퐁당')는 연속수련 상한과 직결됩니다.

### 3.4 UI 요구사항

전공의 근무 화면은 일반 직원과 **다른 대시보드**여야 합니다.

```
┌─ 전공의 수련시간 현황 ─────────────────────┐
│ 이번 주      ████████░░  {n}h / 상한 {N}h  │
│ 4주 평균     ███████░░░  {n}h / 상한 {N}h  │
│ 최장 연속수련 ██████░░░░  {n}h / 상한 {N}h  │
│ 이번 주 당직  ●●○         2회 / 상한 {N}회  │
│ 이번 달 휴일  ●●●○        3일 / 최소 {N}일  │
└────────────────────────────────────────────┘
```

## 4. 근무유형(Shift Type) 모델

### 4.1 기본 3교대

| 코드 | 명칭 | 일반적 시간대 | 야간 포함 |
|---|---|---|---|
| `D` | Day (데이) | 07:00 ~ 15:00 | 없음 |
| `E` | Evening (이브닝) | 15:00 ~ 23:00 | 22:00~23:00 (1h) |
| `N` | Night (나이트) | 22:00 ~ 08:00 | 22:00~06:00 (8h) |
| `O` | Off (휴무) | — | — |

시간대는 **기관마다 다릅니다.** 07:00 시작인 곳도, 06:30 시작인 곳도 있습니다. 반드시 설정값이어야 합니다.

### 4.2 병원 고유 근무유형

| 코드 | 명칭 | 특징 |
|---|---|---|
| `ND` | 나이트 전담 | 야간만 근무. 야간전담간호사 관리료 요건과 연결. |
| `DUTY` | 당직 | 정규 근무 후 이어지는 대기·근무. **대기시간과 실근로시간 분리 필요.** |
| `ONCALL` | 온콜 | 호출 대기. 자택 대기 가능. 호출 시에만 근로시간 산입이 일반적. ⚖️ 검토필요 |
| `12D` / `12N` | 12시간 2교대 | 응급실·중환자실에서 사용. |
| `MID` | 미들 근무 | 피크 시간대 보강 (예: 11:00~19:00). |
| `EDU` | 교육 | 보수교육·원내교육. 근로시간 산입 여부 정책 설정. |
| `A` | 연차 | 휴가 소진. |

### 4.3 당직·온콜의 근로시간 산정 — 가장 까다로운 부분

대기시간이 근로시간인지는 **사용자의 지휘·감독 하에 있는지**로 판단하는 것이 일반적입니다. 실무적으로:

| 유형 | 대기 장소 | 일반적 취급 | 시스템 처리 |
|---|---|---|---|
| 병원 내 당직 (숙직실 대기) | 원내 | 근로시간으로 보는 경향이 강함 | 전체를 근로시간으로 집계하되 정책으로 조정 가능 |
| 온콜 (자택 대기) | 원외 | 대기는 미산입, **호출 응대 시간만** 산입하는 경향 | 호출 발생 기록을 별도 입력 → 그 시간만 집계 |

**구현:**
```
ShiftType.dutyMode = FULL_WORK | CALL_ONLY | POLICY_RATIO
  FULL_WORK    : 전 시간 근로시간
  CALL_ONLY    : 호출 기록(CallEvent)의 합만 근로시간
  POLICY_RATIO : 전체 × 계수 (기관 노사합의로 정한 경우)
```

- `CALL_ONLY`인 경우 **호출 기록 UI가 반드시 쉬워야** 합니다. 새벽에 호출받은 의사가 앱에서 3탭으로 "호출 시작/종료"를 남길 수 있어야 합니다. 이게 어려우면 데이터가 안 쌓이고 기능 전체가 무용지물이 됩니다.
- ⚖️ 검토필요: 당직·온콜의 근로시간성은 다툼이 많은 영역입니다. 제품은 **기관이 자신의 정책을 설정**하게 하고, 그 정책과 근거를 기록으로 남기는 것까지가 역할입니다. 제품이 법적 판단을 대신하면 안 됩니다.

## 5. 연차유급휴가 규칙

상세 산정 로직은 [07. 휴가 관리](07-leave-management.md)에 있습니다. 여기서는 규칙 항목만 정리합니다.

| 규칙 코드 | 내용 | 근거(확인 필요) |
|---|---|---|
| `ANNUAL_LEAVE_BASE` | 1년간 80% 이상 출근 시 15일 | 근기법 §60① |
| `ANNUAL_LEAVE_UNDER_1Y` | 1년 미만 또는 80% 미만 출근 시, 1개월 개근당 1일 | 근기법 §60② |
| `ANNUAL_LEAVE_EXTRA` | 3년 이상 계속근로 시, 최초 1년 초과 매 2년마다 1일 가산 (총 25일 한도) | 근기법 §60④ |
| `LEAVE_PROMOTION` | 사용촉진 절차를 거치면 미사용 수당 지급의무 면제 가능 | 근기법 §61 |
| `COMP_LEAVE` | 연장·야간·휴일근로에 대해 수당 대신 보상휴가 (서면합의 필요) | 근기법 §57 |

**3교대 특유의 논점 — 연차 1일은 몇 시간인가?**

8시간 근무자는 자명하지만, 12시간 교대 근무자가 연차 1일을 쓰면 12시간을 쉬는 것인지 8시간인지가 문제됩니다. 기관 정책으로 다음 중 선택하게 합니다.

```
LeavePolicy.dayEquivalence =
  FIXED_8H          | 연차 1일 = 8시간. 12h 시프트에 쓰면 1.5일 차감
  SHIFT_LENGTH      | 연차 1일 = 해당 시프트 길이. 12h 써도 1일 차감
  CONTRACTUAL_DAILY | 연차 1일 = 근로계약상 1일 소정근로시간
```
⚖️ 검토필요: 근로자에게 불리한 방식은 분쟁 소지가 있습니다.

## 6. ⭐ 수가 연동 규칙 (의료 특화 차별점)

병원의 근태 데이터는 건강보험 수가 산정의 근거가 됩니다. 이것이 범용 HR SaaS와의 결정적 차이입니다.

### 6.1 간호관리료 차등제 (간호등급제)

- 병상 수 대비 간호사 수의 비율로 등급을 산정하고, 등급에 따라 입원료 등에 가산·감산이 적용됩니다.
- **산정 기준의 핵심**: 분기별로, 실제 근무한 간호 인력 수를 신고. 휴직자·파견자·특정 부서 근무자의 산입 여부에 세부 기준이 있습니다.

**시스템이 제공할 것:**
```
간호등급 산정 리포트
├── 대상 기간 (분기)
├── 평균 가동병상 수          [수동 입력 또는 연동]
├── 산정 대상 간호사 수
│    ├── 재직 간호사 목록
│    ├── 제외 대상 (휴직/파견/비해당부서)  ← 규칙 기반 자동 분류 + 수동 조정
│    └── 근무일수 기반 환산 인원
├── 산출 비율 및 예상 등급
└── 신고 서식 초안 (Export)
```

- ⚖️ **검토필요 (중요)**: 산정 기준은 보건복지부 고시(요양급여의 적용기준 및 방법에 관한 세부사항 등)에 규정되어 있으며 **자주 개정됩니다**. 정확한 산입/제외 기준, 환산 방식, 신고 서식은 **현행 고시를 직접 확인**해야 합니다.
- 제품은 **계산을 대신하되 최종 판단은 병원이 하도록** 설계합니다. "이 값으로 신고하세요"가 아니라 "이 데이터로 계산하면 이렇습니다, 검토하세요".
- 고시 개정 대응을 위해 산정 로직도 **버전화된 규칙**으로 구현합니다.

### 6.2 야간전담간호사 관리료 / 야간간호료

- 야간 근무 전담 인력 배치에 대한 별도 수가 항목이 있으며, 인력 요건(전담 인원 수, 야간 근무 비율 등)을 충족해야 합니다.
- 시스템은 근무 기록으로부터 **각 간호사의 야간 근무 비율**을 자동 산출하고, 요건 충족/미달을 표시합니다.
- ⚖️ 검토필요: 요건의 구체적 수치와 산정 방식은 현행 고시 확인 필수.

### 6.3 설계 시사점

수가 리포트는 **돈과 직결되므로 오류의 대가가 큽니다.** 다음 원칙을 지킵니다.

1. **모든 숫자는 클릭하면 근거로 내려갈 수 있어야 함.** "간호사 47.3명"을 클릭하면 47.3이 나온 개인별 근무일수 내역이 보여야 함.
2. **자동 분류는 항상 수동 조정 가능해야 함.** 규칙이 모든 예외를 알 수 없음.
3. **산정 결과에 사용된 고시 버전을 명시.** 나중에 "왜 이렇게 계산됐나" 추적 가능해야 함.
4. **경고를 숨기지 않음.** 데이터가 불완전하면 "이 기간에 근무 기록이 누락된 인원 3명"을 리포트 상단에 표시.

## 7. 규칙 평가 시점과 방식

### 7.1 3단계 평가

| 시점 | 목적 | severity 처리 |
|---|---|---|
| **작성 중 (Realtime)** | 근무표 편집 시 즉시 피드백 | 셀 하이라이트, 저장은 허용 |
| **확정 시 (Commit)** | 근무표 확정 전 최종 검증 | BLOCK 위반 있으면 확정 차단 (사유 입력 시 강행 옵션) |
| **사후 (Actual)** | 실제 기록 기준 재검증 | 경보 발송, 대시보드 표시 |

**계획(근무표) 기준 검증과 실적(출퇴근 기록) 기준 검증은 반드시 분리되어야 합니다.** 계획은 지켰는데 실제로 위반한 경우가 실무에서 대부분입니다.

### 7.2 위반 처리 원칙

```
위반 발견 → 차단이 목적이 아니라 "기록과 인지"가 목적
```

- 병원은 인력난으로 위반이 불가피한 상황이 실제로 발생합니다. 시스템이 무조건 막으면 사용자는 **시스템 밖에서 일하게 되고**, 그러면 기록이 사라져 오히려 리스크가 커집니다.
- 따라서: BLOCK 위반도 **사유를 입력하면 진행 가능**하게 하되, 그 사유와 승인자를 기록합니다. 이 기록 자체가 병원에 가치 있는 자산이 됩니다.

### 7.3 규칙 엔진 인터페이스

```typescript
interface RuleContext {
  tenantId: string;
  worksiteId: string;
  member: { jobFamily: JobFamily; employmentType: EmploymentType; hireDate: Date };
  period: { from: Date; to: Date };
  basis: 'PLANNED' | 'ACTUAL';
}

interface Violation {
  ruleCode: string;
  severity: 'BLOCK' | 'WARN' | 'INFO';
  message: string;          // 사용자 언어. "3/15 나이트 후 3/16 데이 — 휴식 8시간 (최소 11시간)"
  legalBasis: string;       // "근로기준법 제59조 제2항"
  subjects: EntityRef[];    // 관련된 근무 배정/기록
  suggestion?: string;      // "3/16을 오프로 변경하면 해소됩니다"
}

interface RuleEngine {
  evaluate(ctx: RuleContext, data: Timesheet | Roster): Promise<Violation[]>;
}
```

`message`와 `suggestion`이 중요합니다. "규칙 위반"만 뜨는 시스템은 아무도 안 씁니다. **무엇이, 왜, 어떻게 하면 해결되는지**를 말해야 합니다.
