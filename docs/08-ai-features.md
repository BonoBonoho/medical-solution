# 08. AI 기능

## 1. 설계 원칙 — LLM과 최적화 엔진의 역할 분리

이 제품의 AI에서 가장 중요한 결정입니다.

```
❌  LLM에게 근무표를 직접 만들게 한다
    → 그럴듯하지만 규칙을 위반한 표가 나온다
    → 병원에서 이건 법 위반이자 환자 안전 문제

✅  LLM은 "이해"와 "설명"을 담당
    제약을 만족하는 해의 "생성"은 제약 최적화 엔진(CP-SAT)이 담당
```

| 작업 | 담당 | 이유 |
|---|---|---|
| 자연어 요청 → 구조화 제약 | **LLM** (Claude) | 언어 이해는 LLM이 압도적으로 잘함 |
| 제약을 만족하는 근무표 생성 | **OR-Tools CP-SAT** | 결정론적, 검증 가능, 제약 위반 0 보장 |
| 결과 설명 / 미충족 사유 안내 | **LLM** | 사람이 읽을 수 있는 설명 |
| 규정 Q&A | **LLM + RAG** | 근거 문서 인용 필수 |
| 이상 근태 탐지 | **규칙 + 통계** (초기) | 설명 가능해야 함. LLM 불필요 |

### 2.2 CP-SAT 모델 정의

**결정 변수**
```python
# x[m, d, s] = 1 이면 구성원 m 이 d일에 s근무를 배정받음
x = {}
for m in members:
    for d in days:
        for s in shift_types:
            x[m, d, s] = model.NewBoolVar(f"x_{m}_{d}_{s}")
```

**하드 제약 (반드시 만족)**

| 제약 | 표현 |
|---|---|
| 1인 1일 1근무 | `sum(x[m,d,s] for s) == 1` |
| 확정 휴가/오프 고정 | `x[m,d,LEAVE] == 1` |
| 시간대별 최소 인력 | `sum(x[m,d,s] for m) >= demand[d,s].min` |
| 자격 요건 | 자격 미보유자는 해당 근무 변수 = 0 |
| 금지 패턴 (E→D 등) | `x[m,d,E] + x[m,d+1,D] <= 1` |
| 연속 야간 상한 | 슬라이딩 윈도우 합 제약 |
| 시프트 간 최소 휴식 11h | 금지 패턴 집합으로 전개 |
| 주간 근로시간 상한 | `sum(hours[s] * x[m,d,s] for d in week) <= limit` |
| 휴직자 배제 | 해당 구성원의 모든 변수 = 0 |
| 직전월 경계 | 8/31 나이트면 9/1 데이 금지 |

**소프트 제약 (가중치 목적함수)**

| 제약 | 기본 가중치 | 설명 |
|---|---|---|
| 희망휴무 반영 | 100 | 미반영 시 페널티 |
| 나이트 횟수 균등 | 80 | 개인별 나이트 수 편차 최소화 |
| 주말 오프 균등 | 60 | 특정인만 주말 근무 방지 |
| 근무 패턴 연속성 | 50 | D-D-D 처럼 묶이는 것이 낫다 |
| 프리셉터 페어링 | 90 | 신규는 프리셉터와 같은 듀티 |
| 이상 인력 도달 | 40 | 최소는 넘되 이상 인력에 근접 |
| 연차 소진 유도 | 30 | 소멸임박 연차 보유자 배려 |

```python
model.Maximize(sum(w * satisfied_var for w, satisfied_var in soft_terms))
solver.parameters.max_time_in_seconds = 60
solver.parameters.num_search_workers = 8
```

**가중치는 병동별 설정값**이어야 합니다. 중환자실과 외래는 우선순위가 완전히 다릅니다.

### 2.3 타임박스가 중요한 이유

간호사 스케줄링은 NP-hard입니다. 50명 × 30일 × 5근무유형 = 7,500 변수. 최적해를 찾으려면 몇 시간이 걸릴 수 있습니다.

**전략: 60초 안에 "충분히 좋은 해"를 준다.**

```
0~10초  : 첫 실행가능해(feasible) 발견 → 즉시 스트리밍
10~60초 : 목적함수 개선 → 개선될 때마다 스트리밍
60초    : 종료, 최선의 해 반환
```

사용자는 진행 상황을 보면서 기다리고, 마음에 들면 60초를 기다리지 않고 중단할 수 있습니다.

**실행 불가능(INFEASIBLE)한 경우가 실무에서 자주 발생합니다.** 인력이 부족한데 최소 인력 제약을 만족할 수 없는 경우입니다. 이때 "불가능합니다"만 반환하면 쓸모없습니다. 다음을 해야 합니다.

```
INFEASIBLE 처리
 ① 하드 제약을 소프트로 완화하며 재시도 (완화 우선순위 설정)
 ② 어떤 제약을 완화해야 풀리는지 식별
 ③ 사용자에게 제시:
    "현재 조건으로는 근무표를 만들 수 없습니다.
     9/12, 9/13 데이 근무에 각 1명이 부족합니다.
     다음 중 하나가 필요합니다:
       · 최소 인력을 5명 → 4명으로 조정
       · 해당일 오프 신청 2건 중 1건 조정
       · 타 병동 지원 인력 1명"
```

### 2.4 자연어 제약 파싱 (Claude API)

**모델**: `claude-opus-5`
**핵심**: 구조화 출력(structured outputs)으로 스키마를 강제해 파싱 오류를 원천 차단합니다.

```python
import anthropic
from pydantic import BaseModel
from typing import Literal

class ParsedConstraint(BaseModel):
    type: Literal[
        "NO_SHIFT", "PREFER_SHIFT", "FIXED_ASSIGNMENT", "MAX_CONSECUTIVE",
        "PAIR_WITH", "MIN_STAFF_OVERRIDE", "FORBIDDEN_PATTERN", "UNKNOWN"
    ]
    target_member_names: list[str]
    target_dates: list[str]          # ISO date, 빈 배열이면 전체 기간
    shift_codes: list[str]
    params: dict
    is_hard: bool
    confidence: float                # 0.0 ~ 1.0
    source_text: str                 # 원문 중 근거가 된 부분
    clarification_needed: str | None # 애매하면 되물을 질문

class ParseResult(BaseModel):
    constraints: list[ParsedConstraint]
    unparsed_text: list[str]         # 해석하지 못한 부분

client = anthropic.Anthropic()

response = client.messages.parse(
    model="claude-opus-5",
    max_tokens=8000,
    thinking={"type": "adaptive"},
    output_config={"effort": "high"},
    system=CONSTRAINT_PARSER_SYSTEM_PROMPT,
    messages=[{
        "role": "user",
        "content": build_parse_prompt(
            natural_language=user_input,
            members=member_roster,        # 이름 매칭용
            shift_types=shift_type_list,  # 근무유형 코드 매칭용
            period=period,
        ),
    }],
    output_format=ParseResult,
)

parsed = response.parsed_output
```

**시스템 프롬프트 설계 포인트**

```
당신은 병원 간호 근무표 작성 요청을 구조화된 제약 조건으로 변환합니다.

규칙:
1. 제공된 구성원 명단에 없는 이름은 매칭하지 마십시오.
   동명이인이 있으면 clarification_needed에 확인 질문을 넣으십시오.
2. 날짜 표현("셋째 주 금요일", "다음 주", "월말")은 주어진 기간 기준으로
   구체적 날짜로 변환하십시오. 애매하면 confidence를 낮추십시오.
3. 요청자가 "반드시", "절대"라고 하면 is_hard=true,
   "가능하면", "웬만하면"이면 is_hard=false 로 설정하십시오.
   명시가 없으면 개인 요청은 false, 인력 기준은 true 를 기본값으로 하십시오.
4. 해석할 수 없는 문장은 임의로 추측하지 말고 unparsed_text에 넣으십시오.
5. 법정 제약(근로시간, 휴식시간)에 관한 요청은 UNKNOWN으로 분류하십시오.
   법정 제약은 시스템이 별도로 적용하며 사용자가 변경할 수 없습니다.
```

**5번이 특히 중요합니다.** 사용자가 "이번 달은 좀 빡세게 돌려주세요"라고 해도 LLM이 법정 휴식시간 제약을 풀면 안 됩니다.

**파싱 결과를 반드시 사용자에게 확인시킵니다.**

```
┌────────────────────────────────────────────────┐
│ 요청사항을 이렇게 이해했습니다. 맞나요?         │
│ ────────────────────────────────────────────── │
│ ✓ 김수진 — 9월 전체 나이트 근무 제외    [필수]  │
│ ✓ 9/19(금) 이브닝 최소 인원(3명)으로   [희망]  │
│ ✓ 이하늘, 박지원 — 프리셉터와 동일 듀티 [희망]  │
│                                                │
│ ⚠️ 확인 필요                                    │
│   "박간호사"가 두 명입니다.                     │
│   [ 박지원 ] [ 박서연 ] 중 선택해 주세요        │
│                                                │
│         [ 수정하기 ]    [ 이대로 생성 ]         │
└────────────────────────────────────────────────┘
```

LLM 파싱은 틀릴 수 있습니다. **틀렸을 때 사용자가 즉시 알 수 있게** 하는 것이 신뢰의 조건입니다.

### 2.5 프롬프트 캐싱

컨텍스트(구성원 명단, 근무유형, 시스템 프롬프트)는 같은 병동에서 반복됩니다. 프롬프트 캐싱으로 비용과 지연을 줄입니다.

```python
system=[{
    "type": "text",
    "text": CONSTRAINT_PARSER_SYSTEM_PROMPT + ward_context,
    "cache_control": {"type": "ephemeral"},
}]
```

- 캐시는 **접두사 일치**입니다. 병동 컨텍스트를 시스템 프롬프트 뒤쪽에 두고, 매번 바뀌는 자연어 요청은 user 메시지에 둡니다.
- 캐시 적중은 `response.usage.cache_read_input_tokens` 로 확인합니다.
- ⚠️ 시스템 프롬프트에 `datetime.now()` 같은 값을 넣으면 캐시가 매번 무효화됩니다.

### 2.6 피드백 학습

관리자가 AI 결과를 수정한 내역(`schedule_feedback`)이 쌓이면 다음 달 생성 품질이 올라갑니다.

```
학습 대상 (초기에는 ML이 아니라 규칙 추출)
 ├─ 특정 구성원의 반복 수정 → scheduling_constraint 후보 제안
 │   "지난 3개월간 김OO의 나이트를 매번 오프로 바꾸셨습니다.
 │    '나이트 제외'를 상시 제약으로 등록할까요?"
 ├─ 특정 패턴의 반복 수정 → 소프트 제약 가중치 자동 조정 제안
 └─ 특정 날짜의 반복 수정 → 병동 고유 이벤트(회의, 교육) 캘린더화 제안
```

**자동 적용하지 않고 제안합니다.** 관리자가 왜 수정했는지는 시스템이 알 수 없고, 잘못 학습하면 신뢰를 잃습니다.

### 2.7 평가 지표

| 지표 | 측정 방법 | 목표 |
|---|---|---|
| 셀 수용률 | 확정본 대비 AI 생성본이 그대로 유지된 셀 비율 | 85% 이상 |
| 하드 제약 위반 | 생성 결과의 규칙 엔진 재검증 | **항상 0** |
| 오프 신청 반영률 | MUST_OFF 반영 / 전체 MUST_OFF | 95% 이상 |
| 나이트 배분 지니계수 | 개인별 나이트 수 불균등도 | 0.15 이하 |
| 생성 시간 | p95 | 60초 이내 |
| INFEASIBLE 비율 | 실행불가 반환 비율 | 10% 이하 |

**하드 제약 위반 0은 타협 불가입니다.** 생성 후 반드시 규칙 엔진으로 재검증하고, 위반이 발견되면 결과를 반환하지 않고 오류로 처리합니다.

## 3. 이상 근태 탐지

### 3.1 초기 접근: 규칙 + 통계 (LLM 아님)

**LLM을 쓰지 않는 이유**: 이 기능의 결과는 사람에 대한 의심입니다. **왜 걸렸는지 정확히 설명할 수 없으면 쓰면 안 됩니다.** 규칙 기반이면 "직전 기록 위치에서 30분 만에 200km 이동"처럼 명확히 설명됩니다.

탐지 신호는 [06. 모바일 출퇴근 §8](06-mobile-attendance.md#8-이상-탐지-신호) 참고.

```python
SIGNALS = [
    ImpossibleTravelRule(max_speed_kmh=150),
    SharedDeviceRule(),
    IdenticalCoordinateRule(threshold=5),   # 소수점까지 동일한 기록 5회 이상
    UnscheduledCheckInRule(),
    ExactTimingRule(tolerance_seconds=2, occurrences=10),
    OfflineQueueRatioRule(threshold=0.5),
    SequenceGapRule(),
]

def detect(member_id, period):
    findings = []
    for rule in SIGNALS:
        result = rule.evaluate(member_id, period)
        if result.triggered:
            findings.append({
                "rule": rule.code,
                "severity": result.severity,     # LOW | MEDIUM | HIGH
                "evidence": result.evidence,     # 사람이 검토 가능한 원자료
                "explanation": result.explain(), # 한국어 설명
            })
    return findings
```

### 3.2 UI 원칙

```
❌ "부정 출근 의심자: 김OO"
✅ "확인이 필요한 기록 3건"
```

- **알고리즘이 사람을 단정하지 않습니다.** 관리자에게 "확인해 보세요"라고 말할 뿐입니다.
- 근거 원자료(기록 시각, 위치, 기기)를 항상 함께 보여줍니다.
- 관리자가 "정상으로 확인" 처리하면 같은 패턴은 다음부터 억제합니다.
- ⚖️ 검토필요: 근태 모니터링 결과를 인사 불이익에 활용하려면 취업규칙 근거와 절차가 필요합니다.

### 3.3 향후: ML 도입 시점

6개월 이상 데이터가 쌓이고 관리자의 "정상/이상" 라벨이 축적되면 지도학습을 검토합니다. 그때도 **설명 가능한 모델**(결정트리, 규칙 추출 가능한 모델)을 우선합니다.

## 4. 초과근무 리스크 예측

### 4.1 접근

복잡한 ML이 필요 없습니다. 계획(근무표) + 실적(현재까지 기록)으로 선형 외삽하면 충분히 정확합니다.

```python
def predict_weekly_overrun(member_id, week_start):
    actual = get_actual_minutes(member_id, week_start, today)
    planned_remaining = get_planned_minutes(member_id, tomorrow, week_end)

    # 이 사람의 최근 8주 "계획 대비 실제 초과분" 중앙값
    drift_ratio = get_historical_drift(member_id, weeks=8)

    projected = actual + planned_remaining * (1 + drift_ratio)
    limit = rule_engine.weekly_limit(member_id, week_start)

    return {
        "projected_minutes": projected,
        "limit_minutes": limit,
        "risk": "HIGH" if projected > limit else
                "MEDIUM" if projected > limit * 0.9 else "LOW",
        "drift_ratio": drift_ratio,   # 설명 가능성 확보
    }
```

`drift_ratio`가 핵심입니다. 근무표상 8시간인데 실제로는 매번 9시간 일하는 사람이 있습니다. 이 개인차를 반영해야 예측이 맞습니다.

### 4.2 경보 흐름

```
주 초반 (월/화) → 예측만, 알림 없음
주 중반 (수/목) → HIGH 위험자를 관리자 대시보드에 표시
              → 병동 관리자에게 알림 "김OO 이번 주 52시간 초과 예상"
초과 임박      → 본인 + 관리자 즉시 알림
초과 발생      → 위반 기록 생성, 사유 입력 요구
```

**주 초반에 알리지 않는 이유**: 오탐이 많고, 알림 피로가 생기면 정작 중요할 때 무시됩니다.

## 5. HR 어시스턴트 (RAG)

### 5.1 용도

직원이 "연차가 몇 개 남았고 언제까지 써야 하나요?", "경조사 휴가는 며칠인가요?" 같은 질문을 인사팀에 물어보는 것을 줄입니다. 중소 병원은 인사 담당이 1~2명이라 이 문의 부담이 실재합니다.

### 5.2 구조

```
질문
 │
 ▼
① 의도 분류 (개인 데이터 조회 vs 규정 질문 vs 기타)
 │
 ├─ 개인 데이터 조회 → Tool Use로 API 호출
 │    "제 연차 몇 개 남았나요?" → get_leave_balance(member_id)
 │    ※ 반드시 요청자 본인의 데이터만. 권한 검증은 API 레이어에서.
 │
 ├─ 규정 질문 → RAG
 │    취업규칙, 인사규정, 복무규정을 청킹 → pgvector 임베딩
 │    유사 청크 검색 → Claude에 근거로 제공
 │
 └─ 기타 → "인사팀에 문의해 주세요" + 담당자 연결
```

### 5.3 구현

```python
response = client.messages.create(
    model="claude-opus-5",
    max_tokens=4000,
    thinking={"type": "adaptive"},
    system=[{
        "type": "text",
        "text": HR_ASSISTANT_SYSTEM_PROMPT,
        "cache_control": {"type": "ephemeral"},
    }],
    tools=[
        {
            "name": "get_my_leave_balance",
            "description": "질문한 본인의 잔여 연차와 소멸 예정일을 조회합니다.",
            "input_schema": {"type": "object", "properties": {}},
        },
        {
            "name": "search_hr_policy",
            "description": (
                "취업규칙·인사규정에서 관련 조항을 검색합니다. "
                "규정에 관한 질문에는 반드시 이 도구를 먼저 사용하십시오."
            ),
            "input_schema": {
                "type": "object",
                "properties": {"query": {"type": "string"}},
                "required": ["query"],
            },
        },
    ],
    messages=conversation,
)
```

**시스템 프롬프트의 필수 항목**

```
1. 규정에 관한 답변은 반드시 search_hr_policy 로 검색한 내용에 근거해야 합니다.
   검색 결과에 없는 내용은 "규정에서 확인되지 않습니다. 인사팀에 문의해 주세요"
   라고 답하십시오. 일반적인 노동법 지식으로 답변하지 마십시오.
2. 답변에는 항상 근거 조항(예: 취업규칙 제32조)을 명시하십시오.
3. 다른 직원의 개인정보(급여, 연차, 인사기록)는 어떤 경우에도 답하지 마십시오.
4. 법률 해석이나 분쟁 소지가 있는 질문(부당해고, 임금체불 등)에는
   답변하지 말고 인사팀 또는 공인노무사 상담을 안내하십시오.
5. 확실하지 않으면 추측하지 말고 모른다고 답하십시오.
```

**1번과 4번이 특히 중요합니다.** HR 챗봇이 잘못된 법률 정보를 주면 회사가 책임을 지게 됩니다. 그리고 병원마다 취업규칙이 다르므로 **일반 지식으로 답하면 반드시 틀립니다.**

## 6. 인사 문서 자동 생성 (Could)

근로계약서, 인사발령문, 재직증명서 초안 생성.

- 템플릿 + 구조화 데이터 치환이 기본. LLM은 **비정형 항목(발령 사유 문안 등)에만** 사용.
- **생성된 문서는 반드시 담당자 검토 후 발행.** 자동 발행 금지.
- 근로계약서는 법정 명시사항 누락 시 과태료 대상이므로, 필수 항목 체크리스트를 코드로 검증합니다.

## 7. 인력 수요 예측 (Could)

과거 환자 수·계절성 기반으로 필요 인력을 예측해 근무표 생성의 `demand` 입력으로 사용.

- 초기: 과거 3년 동월 평균 + 요일 계수. 단순하지만 실용적.
- 이후: Prophet 또는 LightGBM.
- **입원환자 수 데이터가 필요한데 이는 EMR/OCS 영역**입니다. [00. 제품 개요 §6](00-product-overview.md#6-명시적-비목표-non-goals)의 비목표와 충돌하므로, **집계된 일별 환자 수만 CSV/API로 받는 형태**로 제한합니다. 개별 환자 정보는 절대 받지 않습니다.

## 8. 이직 위험 신호 (Could) — 신중히

근태 데이터로 이직 위험을 예측할 수 있습니다. 초과근무, 연차 미사용, 야간 편중, 주말 근무 집중 등이 신호입니다.

**하지만 이 기능은 오용되면 제품을 파괴합니다.**

### 8.1 강제 원칙

| 원칙 | 이유 |
|---|---|
| **개인별 위험 점수를 관리자에게 노출하지 않음** | 낙인 효과. "이 사람 나갈 것 같으니 중요 업무 빼자"가 됨 |
| **부서/병동 단위 집계만 제공** | "3병동 야간 편중이 심화되고 있습니다" |
| **개선 액션과 항상 함께 제시** | 문제 지적만 하는 지표는 관리자를 불안하게만 함 |
| **인사평가·계약갱신 데이터로 Export 불가** | 시스템 레벨에서 차단 |

```
✅  "3병동: 최근 3개월 야간 근무가 특정 3명에게 62% 집중되어 있습니다.
     야간 배분 균등화 가중치를 높이면 개선됩니다. [설정 이동]"

❌  "이간호사 이직 위험도 78% (높음)"
```

### 8.2 우선순위

**후순위입니다.** 핵심 기능이 안정되고, 고객사와 이 기능의 사용 원칙에 합의한 뒤에만 개발합니다.

## 9. AI 인프라 공통 사항

### 9.1 서비스 구성

```
AI Service (Python FastAPI, VPC 내부, mTLS)
├── /internal/ai/schedule/generate      # CP-SAT + Claude
├── /internal/ai/schedule/parse         # 자연어 제약 파싱만
├── /internal/ai/anomaly/detect         # 규칙 기반
├── /internal/ai/forecast/overtime      # 통계
└── /internal/ai/assistant/query        # RAG
```

### 9.2 장애 대응

| 상황 | 동작 |
|---|---|
| Claude API 장애 | 자연어 파싱 없이 **구조화 제약만으로 CP-SAT 실행**. AI 생성 자체는 계속 동작. |
| CP-SAT 타임아웃 | 중간 해가 있으면 반환, 없으면 INFEASIBLE 처리 후 원인 분석 제공 |
| AI 서비스 전체 장애 | 근무표 수동 편집·근태·휴가 등 **코어 기능은 정상 동작**. AI는 부가 기능. |

**AI 장애가 근태 기록을 막으면 안 됩니다.** 아키텍처에서 AI 서비스를 분리한 핵심 이유입니다.

### 9.3 비용 관리

| 항목 | 통제 방법 |
|---|---|
| 자연어 파싱 | 프롬프트 캐싱, 테넌트당 시간당 10회 제한 |
| HR 어시스턴트 | 대화 턴 수 제한, 캐싱, `effort: "medium"` |
| CP-SAT | 컴퓨트 비용. 타임박스로 상한 고정 |

토큰 사용량은 `response.usage`로 테넌트별 집계해 요금제 설계의 근거로 씁니다.

### 9.4 데이터 취급

| 원칙 | 내용 |
|---|---|
| 최소 전송 | LLM에 보내는 컨텍스트에서 **주민번호·연락처·주소를 제외**. 이름은 매칭에 필요하므로 포함하되, 필요 시 익명 ID 치환 옵션 제공. |
| 학습 미사용 | API 요청 데이터가 모델 학습에 사용되지 않음을 계약·문서로 명시 |
| 로깅 | 프롬프트 전문을 로그에 남기지 않음. 요청 ID와 토큰 사용량만 기록. |
| 국외 이전 | Claude API 호출은 국외 이전에 해당할 수 있음. ⚖️ **검토필요** — 개인정보 처리방침 고지 및 동의 절차 확인. 익명 ID 치환으로 개인정보 전송 자체를 피하는 설계를 우선 검토. |

마지막 항목은 병원 고객이 반드시 묻는 질문입니다. **이름을 익명 ID로 치환해 LLM에 보내고, 응답을 받은 뒤 다시 매핑하는 구조**를 기본값으로 설계하면 이 논쟁 자체를 피할 수 있습니다.

```
"김수진 간호사 나이트 빼주세요"
  → 치환 → "M014 간호사 나이트 빼주세요"  → Claude
  → 응답 → {target: "M014"} → 역치환 → {target: "김수진"}
```

이 치환은 클라이언트가 아니라 **AI 서비스 진입점에서** 수행합니다.
