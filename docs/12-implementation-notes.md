# 12. 구현 노트

설계 문서(00~11)를 코드로 옮기면서 확인·수정된 사항을 기록한다.
**문서가 틀렸던 부분과 구현 중 새로 결정한 사항**을 남기는 것이 목적이다.

## 2. 구현 중 발견한 설계 결함

### 2.1 규칙 인스턴스를 코드만으로 키잉하면 규칙이 사라진다

**증상**: `KR_NURSING_SHIFT_2026`에 금지 패턴이 두 개(E→D, N→E) 있는데
E→D 규칙이 평가되지 않았다.

**원인**: `resolveRules`가 `Map<RuleCode, Rule>`을 쓰고 있었다. 같은 코드의
두 번째 규칙이 첫 번째를 덮어썼다. 오류도 경고도 없이 조용히 하나가 사라졌다.

**수정**: `RuleDefinition`에 `instanceKey`를 추가하고 해석 키를
`code` 또는 `code#instanceKey`로 바꿨다. 상위 우선순위 규칙 세트가 특정
인스턴스만 끄려면 같은 키를 쓰면 된다.

**시사점**: [02. 도메인 규칙 §1](02-domain-rules.md#1-설계-원칙-규칙은-데이터다)의
RuleSet 스키마에 `instanceKey`가 빠져 있었다. 한 코드에 여러 인스턴스가
필요한 규칙(금지 패턴, 허용 도메인 등)은 처음부터 다중 인스턴스를 전제해야 한다.

### 2.2 야간시간은 나이트 근무만의 것이 아니다

e2e 테스트를 쓰면서 `nightMinutes` 기대값을 960분(나이트 2회 × 8시간)으로
잡았다가 틀렸다. 실제 값은 1020분이었다 — **이브닝 근무(15:00~23:00)의
22:00~23:00 한 시간**이 빠져 있었다.

문서에는 [02 §4.1](02-domain-rules.md#41-기본-3교대)에 이미 명시되어 있었지만,
"야간 = 나이트 근무"라는 직관이 계산을 틀리게 만들기 쉽다. 급여에 직결되므로
UI에서도 근무유형별 야간시간을 분해해 보여줘야 한다.

### 2.3 `emitDecoratorMetadata` 의존은 조용히 실패한다

NestJS의 타입 기반 의존성 주입은 `emitDecoratorMetadata`가 필요한데,
esbuild(vitest가 사용)는 이를 지원하지 않는다. 결과적으로 **런타임에
`this.service`가 undefined**가 되어 모든 요청이 500을 반환했다. 컴파일은 통과한다.

`@Inject(Token)`을 명시하는 방식으로 바꿔 빌드 도구 의존을 제거했다.
[03. 아키텍처](03-architecture.md)의 스택 선택에 이 제약을 반영해야 한다.

### 2.4 ★ 수퍼유저로 접속하면 RLS가 통째로 무시된다 — 경고도 없이

가장 위험했던 발견이다.

[03. 아키텍처 §3.1](03-architecture.md)과 [10. 보안 §4.3](10-security-compliance.md)에서
"애플리케이션 필터링만 믿지 않고 PostgreSQL RLS를 최종 방어선으로 둔다"고 썼다.
스키마에 `ENABLE` + `FORCE ROW LEVEL SECURITY`와 테넌트 정책을 걸고,
"WHERE 절 없이 조회해도 자기 테넌트만 보인다"는 테스트를 작성했다.

**테스트가 통과하지 않았다.** `SELECT * FROM member`가 4개 테넌트의 행을
전부 돌려줬다. 정책은 분명히 존재했고 `FORCE`도 켜져 있었다.

원인은 접속 롤이었다. 개발 편의로 `postgres` 수퍼유저로 접속하고 있었는데,
PostgreSQL에서 **수퍼유저와 `BYPASSRLS` 속성을 가진 롤은 행 수준 보안을
전부 건너뛴다.** `FORCE ROW LEVEL SECURITY`조차 이들에게는 적용되지 않는다.
오류도, 경고도, 로그 한 줄도 남지 않는다.

이 실수가 운영에서 났다면 어땠을지가 문제다. RLS 테스트를 **작성하지 않은
상태에서** 수퍼유저로 배포했다면, 애플리케이션 레벨 필터링이 모든 것을
가려주는 동안 DB 방어선은 존재하지 않는 채로 돌아갔을 것이다. 방어선이
무너진 걸 알게 되는 시점은 애플리케이션에 버그가 하나 생겼을 때, 즉
다른 병원의 인사 데이터가 실제로 노출된 뒤다.

**조치**

| 변경 | 내용 |
|---|---|
| 롤 분리 | `mediwork_app`을 `NOSUPERUSER NOBYPASSRLS`로 생성. 애플리케이션은 이 롤로만 접속 |
| 커넥션 분리 | `DATABASE_URL`(앱) / `DATABASE_ADMIN_URL`(마이그레이션·시드) |
| 코드 분리 | `PgStore(db, adminDb?)` — 스키마 생성·시드는 adminDb로만 가능 |
| 회귀 방지 | `rolsuper = false AND rolbypassrls = false`를 확인하는 테스트 추가 |

마지막 항목이 핵심이다. **격리 테스트가 전부 통과해도 접속 롤이 수퍼유저면
그 통과는 아무 의미가 없으므로, 롤 자체를 검사하는 테스트가 있어야 한다.**
이 테스트가 없으면 나머지 10개 RLS 테스트는 "통과했다"는 착각만 준다.

### 2.5 turbo가 환경변수를 걸러 PostgreSQL 테스트가 조용히 스킵됐다

`pnpm check`가 "7 tasks successful"을 찍는데, 로그를 보니 RLS 테스트 11개가
전부 `skipped`였다. `DATABASE_URL`을 분명히 export한 상태였다.

Turbo 2는 캐시 정확성을 위해 **선언되지 않은 환경변수를 태스크에 전달하지
않는다.** 테스트 파일은 `DATABASE_URL === undefined`를 보고 `describe.skip`을
탔고, 결과는 초록색이었다.

`turbo.json`의 `test` 태스크에 `env: ["DATABASE_URL", "DATABASE_ADMIN_URL"]`을
선언해 해결했다. §2.4와 같은 종류의 사고다 — **검증이 돌지 않았는데 통과로
보이는 것**이 검증이 실패하는 것보다 위험하다.

### 2.6 멱등성은 애플리케이션 조회만으로 부족하다

`clientNonce`로 기존 레코드를 먼저 조회하는 방식은 순차 재시도에는 통하지만,
동시 요청 두 개가 조회를 동시에 통과하면 둘 다 삽입한다. 지하철에서 신호가
끊겼다 붙으며 재시도가 겹치는 상황은 실제로 일어난다.

DB에 부분 유니크 인덱스(`WHERE client_nonce IS NOT NULL`)를 걸고, 삽입이
`23505`로 실패하면 기존 레코드를 조회해 돌려주도록 했다. e2e에 동시 요청
두 건이 같은 `id`를 받는지 확인하는 테스트가 있다.

### 2.7 그리드를 만들자 "계산은 한 벌" 원칙이 실제로 시험됐다

근무표 그리드는 셀 하나를 바꿀 때마다 위반을 다시 보여줘야 한다. 여기서
선택지가 두 개뿐인 것처럼 보인다.

| 방법 | 문제 |
|---|---|
| 편집할 때마다 서버에 물어본다 | 30명 × 31칸을 채우는 동안 900번 왕복. 못 쓴다 |
| 웹이 규칙 판정을 따로 구현한다 | 화면과 확정 판정이 갈라진다. 편집 중엔 초록불인데 저장하면 막힌다 |

두 번째가 더 나쁘다. 사용자가 원인을 알 수 없기 때문이다.

세 번째 방법을 택했다. **계산을 도메인 패키지의 순수 함수 하나로 올리고
서버와 웹이 같은 함수를 부른다.**

- `evaluateRosterPlan(plan)`을 `packages/domain/src/roster/`에 신설
- API의 `RosterService.detail()`이 하던 80줄짜리 오케스트레이션을 이 함수로 이관
- API 응답에 `plan`(계산 입력 일체: 구성원·근무유형·배정·공휴일·규칙 세트)을 포함
- 웹은 편집할 때마다 `plan`을 갱신해 같은 함수를 다시 호출

화면의 위반과 서버의 확정 판정이 **정의상** 일치한다. 두 벌을 동기화하는
문제가 아니라 애초에 한 벌이다.

[03. 아키텍처 §8.1](03-architecture.md)에서 "계산 로직은 한 벌만 존재한다"고
썼지만, 그때는 원칙 선언이었다. 실제로 웹을 만들어 보니 이 원칙을 지키려면
**API 응답 설계까지 바뀌어야 했다** — 계산 결과만 내려보내는 API로는 불가능하고,
계산 입력을 내려보내야 한다. 원칙을 문서에 쓰는 것과 지키는 것은 다르다.

부수 효과로 `RosterService`가 훨씬 작아졌고, 도메인 테스트 8개가 추가되면서
그리드 없이도 근무표 평가를 검증할 수 있게 됐다.

### 2.8 "AI가 만들었습니다"는 근로감독에서 변명이 되지 않는다

근무표 생성기를 만들면서 가장 먼저 정한 것은 **LLM에게 근무표를 만들게 하지
않는다**는 것이다. 필요한 것은 그럴듯한 답이 아니라 제약을 만족하는 답이고,
법정 근로시간을 어긴 근무표는 아무리 보기 좋아도 쓸모가 없다.

CP-SAT는 결정론적이고, 제약 만족을 보장하며, 왜 해가 없는지 물어볼 수 있다.
LLM은 셋 다 못 한다. 대신 LLM은 자연어 요청을 구조화 제약으로 바꾸는 일을
맡는다 — LLM이 잘하고 CP-SAT는 못 하는 일이다.

구현하며 확정한 세 가지.

**해가 없을 때 이유를 말한다.** `INFEASIBLE`만 던지면 관리자는 무엇을
고쳐야 할지 알 수 없다. 제약군을 하나씩 빼고 다시 풀어, 빼니까 풀리는
제약을 지목한다. 빼고도 안 풀리면 여러 조건이 얽힌 것이므로 그렇게 말한다.

**해가 없어도 HTTP 200이다.** 4xx로 던지면 클라이언트가 "요청이 잘못됐다"고
해석한다. 요청은 옳고 조건이 서로 모순인 것이므로 구분해야 한다.

**결과를 독립적으로 재검증한다.** CP-SAT는 받은 제약을 어기지 않지만
모델을 잘못 짜는 것은 언제든 가능하다. `verify.py`가 배정 결과를 직접 훑어
같은 제약을 다시 확인한다 — 솔버는 변수와 선형식으로, 검증기는 결과를
순회하는 방식으로, 일부러 다른 방법을 썼다. 검증에 걸리면 결과를 폐기하고
500을 낸다. **잘못된 근무표를 200으로 돌려주면 그대로 확정돼 근로감독까지
간다.**

LLM 쪽도 같은 태도다. 해석 결과는 그대로 쓰지 않고 명단·근무유형·기간에
대조해 검증한 뒤, 확신도가 0.8 미만이면 자동 반영하지 않는다. 이 검증은
LLM 없이 동작하고 테스트로 고정돼 있다 — **LLM이 무엇을 뱉든 검증을
통과하지 못하면 근무표에 영향을 주지 못한다.**

한편 `parse_constraints()`(실제 API 호출)는 이 저장소에서 검증하지 못했다.
키가 없어 호출해 본 적이 없으므로 README와 코드 주석에 그렇게 적어 두었다.
동작하는 것처럼 써 두면 그대로 배포된다.

## 3. 구현하며 확정한 정책

문서에서 "미해결 논점"으로 남겼던 항목 중 코드에 반영된 것들.

| 논점 | 결정 | 근거 |
|---|---|---|
| 연차 1일의 시간 환산 기본값 | `SHIFT_LENGTH` | 직원에게 유리. 불리한 방식은 취업규칙 불이익 변경 절차가 필요할 수 있음 ⚖️ |
| 취소 시 소멸된 부여 건 복원 | `CARRY_FORWARD` | 직원에게 유리. 기관 설정으로 `FORFEIT` 선택 가능 |
| 휴가 잔액 차감 시점 | 신청 시 예약 차감 | 승인 시 차감하면 같은 잔액으로 중복 신청이 가능해짐 |
| 주간 연장근로 산정 | `max(일 단위 합계, 주 단위 초과분)` | 일·주 기준을 모두 적용하되 이중 계산하지 않음 |
| 위치 검증 실패 시 HTTP 상태 | 422 + `data` 동봉 | 앱이 "기록됨/승인대기"를 구분 표시해야 함 |
| `POST /attendance/records` 성공 코드 | 200 (201 아님) | 멱등 재시도 시 기존 레코드를 반환하므로 Created가 아님 |

여전히 미해결인 항목은 [02 §8](02-domain-rules.md#8-미해결-논점-구현-전-결정-필요) 참고.
특히 **인계(handover) 시간 처리**와 **온콜 대기시간 기본 정책**은 파일럿 병원의
실제 운영을 관찰한 뒤 결정해야 한다.

## 4. 코드에 반영된 설계 원칙

문서의 원칙 중 코드로 강제한 것들. 리팩터링 시 깨지지 않게 테스트로 고정했다.

| 원칙 | 강제 방법 | 테스트 |
|---|---|---|
| 계산 로직은 한 벌만 존재한다 | `packages/domain` 순수 함수. 서버가 재구현하지 않음 | 도메인 테스트 132개 |
| 위치 검증 실패해도 기록은 남는다 | `verifyLocation`이 `REJECTED`를 반환하지 않음 | `모의 위치는 승인되지 않지만 거부되지도 않는다` |
| 무결성 실패는 거부가 아니라 강등 | `finalize()`가 `PENDING_REVIEW`로만 낮춤 | `미등록 기기는 승인 대기로 강등된다` |
| BLOCK 위반은 막는 게 아니라 기록한다 | `publish()`가 사유 입력 시 진행 | `사유를 입력하면 강행 확정할 수 있다` |
| 특례 합의 만료 시 52시간 규칙 자동 복귀 | RuleSet의 `effectiveTo` | `서면합의가 만료되면 특례가 꺼지고…` |
| 소수점 오차 없는 연차 계산 | 정수 단위(1일=100) | `반차·반반차를 섞어도 소수점 오차가 없다` |
| 테넌트 격리 (애플리케이션) | 저장소가 컨텍스트 없이는 동작 불가 | `다른 테넌트의 근무표는 조회되지 않는다` |
| 테넌트 격리 (DB) | RLS 정책 + `FORCE` | `WHERE 절 없이 전체 조회해도 자기 테넌트 행만 보인다` |
| RLS 우회 롤로 접속하지 않는다 | `mediwork_app`을 `NOSUPERUSER NOBYPASSRLS`로 생성 | `애플리케이션 롤은 수퍼유저가 아니며 BYPASSRLS도 없다` |
| 감사 로그·근태 원본은 지워지지 않는다 | 애플리케이션 롤에서 `UPDATE`/`DELETE` 권한 회수 | `감사 로그는 애플리케이션 롤이 수정·삭제할 수 없다` |
| 저장소 구현을 바꿔도 동작이 같다 | 같은 e2e를 두 백엔드에 `describe.each` | e2e 27개 × (memory, postgres) |
| 강행 확정은 누가 했는지가 남는다 | `audit_log.actor_id` 기록 | `사유를 입력하면 강행 확정할 수 있다` |
| 화면의 위반과 확정 판정이 갈라지지 않는다 | 서버·웹이 `evaluateRosterPlan` 한 벌 공유 | `같은 입력이면 몇 번을 돌려도 같은 결과다` |
| 위반을 색으로만 표시하지 않는다 | 테두리 + 점 + `aria-label` 병용 | (그리드 CSS·컴포넌트) |
| 설정한 적 없는 규칙으로 근무표를 막지 않는다 | 규칙 세트가 없으면 위반도 없음 | `사업장에 규칙 세트가 없으면 위반도 없다` |
| AI 생성 결과도 하드 제약을 어기면 폐기한다 | 솔버와 다른 방식으로 재검증 | `금지 패턴을 어긴 해를 잡아낸다` |
| 반영하지 못한 요청은 이름·날짜·이유로 보고한다 | `SolveResponse.unmet` | `반영하지 못한 희망휴무는 이름과 날짜로 보고된다` |
| LLM 해석은 검증 없이 반영되지 않는다 | 명단·근무유형·기간 대조 + 확신도 임계값 | `명단에 없는 이름은 버린다` |
| 같은 입력이면 같은 근무표가 나온다 | `random_seed` 지정 시 단일 워커 | `같은 시드로 두 번 풀면 같은 근무표가 나온다` |
| 전공의 규칙은 값 미확정 상태로 출시되지 않는다 | 템플릿을 `isActive: false` + 미래 시행일 | `전공의 템플릿은 값이 확정되지 않아 적용되지 않는다` |
| 승인 대기 처리에 사유 필수 | 컨트롤러 검증 | `사유 없는 처리는 거부한다` |

마지막 두 항목이 특히 중요하다. 전공의 규칙에 임의의 수치를 넣어두면
**그대로 출시될 위험**이 있어, 값이 없으면 아예 적용되지 않도록 만들었다.

## 5. 서버 시간대에 의존하지 않는 이유

`packages/domain/src/time/interval.ts`는 `Date`의 로컬 시간대를 쓰지 않고
오프셋을 명시적으로 받는다. 서버 TZ 설정이 바뀌면 근로시간 계산 결과가
달라지는 사고를 막기 위해서다.

```ts
// ❌ 서버 TZ에 의존 — 컨테이너 설정 하나로 급여가 틀어진다
new Date('2026-07-29 09:00')

// ✅ 오프셋 명시
localDateTime('2026-07-29', '09:00', KST_OFFSET_MINUTES)
```

**한계**: 고정 오프셋 시간대만 지원한다. 한국(UTC+9, 서머타임 없음)은 정확하지만,
서머타임이 있는 지역으로 확장하려면 이 모듈 전체를 IANA 시간대 기반으로
교체해야 한다. 지금 이 제약을 문서화해 두는 이유는, 나중에 "왜 안 되지"를
디버깅하는 대신 곧바로 교체 지점을 찾게 하기 위함이다.

## 6. 다음 구현 단계

로드맵([11. 개발 로드맵](11-roadmap.md)) 기준 현재 위치는 **Phase 1 초반**이다.

### 6.1 바로 이어서 할 것

| 항목 | 이유 |
|---|---|
| **결재 엔진 (범용)** | 휴가·야근·근태수정·스왑이 전부 같은 흐름. 따로 만들면 4벌 중복 |
| **근태 수정 요청** | 실무에서 가장 자주 쓰이는 기능인데 아직 없음 |
| **근무표 편집 저장** | 그리드는 만들었으나 편집 결과가 서버로 가지 않는다 |

### 6.2 착수 전 선행 조건이 있는 것

| 항목 | 선행 조건 |
|---|---|
| 전공의 수련시간 관리 | ⚖️ 현행 전공의법 수치 확정 |
| 수가 리포트 | ⚖️ 현행 고시 확인 + 파일럿 병원 과거 신고자료 대조 |
| 모바일 앱 | iOS/Android WiFi 접근 PoC (Phase 0) |
| PC 사용 통제 | 법적 절차 문서 준비 + 사내 도그푸딩 |
| AI 근무표 생성 | CP-SAT PoC + 수간호사 밀착 관찰로 제약 목록 확보 |

**마지막 항목이 중요하다.** 제약 조건 목록을 상상으로 만들면 반드시 틀린다.
현재 `KR_NURSING_SHIFT_2026`의 제약(E→D 금지, 연속 나이트 3회)은 일반적으로
알려진 것일 뿐, 실제 병동의 제약은 훨씬 많고 구체적이다.
