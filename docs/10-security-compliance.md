# 10. 보안 · 규제 준수

> ⚖️ **이 문서 전체가 법률 검토 대상입니다.** 개인정보보호법, 위치정보법, 근로기준법 관련 내용은 설계 참고용이며 법률 자문이 아닙니다. 서비스 출시 전 개인정보 전문 법무 검토와 공인노무사 검토가 필수입니다.

## 2. 위치정보 처리 (가장 주의할 영역)

### 2.1 ⚖️ 위치기반서비스사업 신고 검토 — 최우선 확인 사항

「위치정보의 보호 및 이용 등에 관한 법률」은 개인위치정보를 이용한 서비스를 제공하는 사업자에게 신고 의무를 부과하고 있습니다.

**출시 전 반드시 확인해야 할 사항:**

1. 우리 서비스가 **위치기반서비스사업 신고 대상**인지
2. 신고 대상이라면 **관할 기관과 신고 절차·요건**
3. 신고 대상이 아니라면 그 근거 (법률 검토 의견서로 보관)
4. 개인위치정보 수집·이용·제공에 필요한 **동의 방식과 고지 항목**
5. 위치정보 **이용·제공 사실 확인자료 보관** 의무 여부와 기간

**이것은 개발 착수 전에 확인해야 합니다.** 나중에 "신고 대상이었다"가 되면 서비스 중단 리스크입니다. MVP 착수 시점에 법무 검토를 병행하는 것을 로드맵에 반영했습니다 ([11 로드맵](11-roadmap.md)).

### 2.2 수집 최소화 설계

법적 리스크를 줄이는 가장 확실한 방법은 **덜 수집하는 것**입니다.

| 항목 | 설계 |
|---|---|
| 수집 시점 | **체크인/체크아웃 버튼을 누른 순간만.** 상시 추적 없음 |
| 백그라운드 위치 | **사용하지 않음.** 'Always' 권한 요청 안 함 |
| 좌표 정밀도 | 검증에 필요한 만큼만. 저장 시 소수점 제한 검토 |
| 원본 보관 | **90일**. 이후 좌표 삭제, 검증 결과만 보존 |
| 이동 경로 | **구성하지 않음.** 시계열 좌표를 연결하는 기능 없음 |

```sql
-- 90일 경과 시 위치 원본 제거 (정기 배치)
UPDATE attendance_record
SET evidence = evidence - 'gps' - 'wifi' - 'beacon'
WHERE work_date < CURRENT_DATE - INTERVAL '90 days'
  AND evidence ? 'gps';
```

근태 기록 자체는 법정 보존기간(3년) 유지하되, **위치 원본은 목적 달성 후 삭제**합니다.

### 2.3 동의 설계

```
앱 최초 실행 시 (권한 요청 전)
┌──────────────────────────────────────────────┐
│  위치정보 이용 동의                            │
│  ─────────────────────────────────────────── │
│  수집 항목                                    │
│    · 출퇴근 기록 시점의 GPS 좌표               │
│    · 출퇴근 기록 시점의 WiFi 접속점 정보        │
│                                              │
│  이용 목적                                    │
│    · 사업장 내 출근 여부 확인                  │
│                                              │
│  보유 기간                                    │
│    · 90일 (이후 자동 삭제)                     │
│                                              │
│  ⓘ 출퇴근 버튼을 누르는 순간에만 확인하며,      │
│    평소 위치는 수집하지 않습니다.               │
│                                              │
│  동의를 거부하실 수 있으며, 이 경우 병동         │
│  키오스크 또는 웹으로 기록할 수 있습니다.        │
│                                              │
│  [ 동의하지 않음 ]        [ 동의 ]             │
└──────────────────────────────────────────────┘
```

**"거부해도 대체 수단이 있다"는 문구가 중요합니다.** 동의가 사실상 강제되면 유효한 동의로 보기 어렵습니다.

## 3. 개인정보 보호

### 3.1 고유식별정보(주민등록번호)

```sql
CREATE TABLE member (
  ...
  rrn_encrypted   bytea,   -- AES-256-GCM, 전용 KMS 키
  rrn_hash        text,    -- HMAC-SHA256, 중복 확인 전용
  ...
);
```

- **평문 저장 절대 금지.** 별도 KMS 키로 암호화하고, 애플리케이션 일반 키와 분리합니다.
- **복호화 권한을 최소화합니다.** 급여 Export, 4대보험 신고 등 실제 필요한 경로에서만.
- 복호화가 발생하면 `audit_log`에 `READ_PII`로 기록합니다.
- **화면에는 항상 마스킹.** `900101-1******`
- ⚖️ 수집 자체가 법령상 근거가 있어야 합니다. 근로소득 원천징수·4대보험 신고 목적이 일반적 근거입니다. **불필요하면 수집하지 않는 것이 최선**이며, 급여를 직접 계산하지 않는 기관에서는 수집을 생략할 수 있게 설정 옵션을 제공합니다.

### 3.2 민감정보

병가 사유(질병명), 산재 관련 정보, 장애 관련 정보는 민감정보입니다.

| 설계 |
|---|
| 휴가 신청 시 **사유 입력을 선택 항목**으로 (필수화 금지) |
| 진단서 등 첨부 파일은 별도 암호화 저장, 접근 권한 제한 |
| 결재자에게도 **사유 상세는 기본 비노출**, "병가" 종류만 표시 |
| 필요 시 인사 담당자만 열람, 열람 이력 기록 |

**"결재자에게도 병명을 보여주지 않는다"**가 실무적으로 중요합니다. 부서장이 부하 직원의 병명을 아는 것은 필요하지도, 적절하지도 않습니다.

### 3.3 접근 통제 (RBAC + 데이터 스코프)

```
역할
 ├─ SUPER_ADMIN   : 테넌트 전체. 계정·설정 관리
 ├─ HR_MANAGER    : 인사·급여 데이터 전체
 ├─ DEPT_HEAD     : 소속 부서 트리 하위
 ├─ WARD_MANAGER  : 담당 병동 (근무표·근태만, 급여 제외)
 └─ MEMBER        : 본인 데이터만

데이터 스코프 = 역할 × 조직 트리 경로(ltree)
```

```sql
-- 부서장은 자기 부서와 하위 부서만
SELECT * FROM member m
JOIN member_assignment ma ON ma.member_id = m.id
JOIN department d ON d.id = ma.department_id
WHERE d.path <@ (SELECT path FROM department WHERE id = :actor_dept_id);
```

**중요한 분리: 병동 관리자는 근무표를 짜지만 급여는 볼 수 없습니다.** 수간호사가 팀원 급여를 보는 것은 부적절하고, 실제 병원에서도 분리되어 있습니다.

### 3.4 감사 로그

```
반드시 기록하는 행위
 ├─ 개인정보 조회 (주민번호, 연락처, 급여 포함 화면)
 ├─ 근태 기록 수정 (원본·수정본·사유·승인자)
 ├─ 휴가 잔액 수동 조정
 ├─ 권한 변경
 ├─ 데이터 Export (범위·건수 포함)
 ├─ PC 사용 개인별 조회 (사유 필수)
 └─ 로그인 / 로그인 실패 / 기기 등록
```

- `audit_log` 테이블에 **INSERT만 허용**. 애플리케이션 DB 사용자에게 UPDATE/DELETE 권한 미부여.
- 3년 이상 보존.
- 관리자도 감사 로그를 삭제할 수 없어야 합니다.

### 3.5 파기

| 데이터 | 보존 | 파기 |
|---|---|---|
| 근로자명부·임금대장·근로계약서 | 3년 (근기법 §42) ⚖️ | 기간 경과 후 파기 |
| 근태 기록 | 3년 | 익명화 후 통계 보존 가능 |
| 위치 원본 | 90일 | 자동 삭제 |
| PC 사용 기록 | 6개월 | 자동 삭제 |
| 감사 로그 | 3년 이상 | 콜드 스토리지 이관 |
| 퇴직자 정보 | 법정 보존기간까지 | 이후 파기 또는 익명화 |

**퇴직자 처리가 자주 누락됩니다.** 퇴직 후 법정 보존기간이 지나면 자동으로 파기 대상 목록에 오르고, 관리자가 확인 후 파기하는 흐름을 만듭니다.

## 4. 기술적 보안 조치

### 4.1 전송·저장

| 계층 | 조치 |
|---|---|
| 전송 | TLS 1.3, HSTS, 인증서 핀닝(모바일) |
| 저장 (DB) | RDS 저장 암호화(KMS) + 민감 컬럼 애플리케이션 레벨 암호화 |
| 저장 (파일) | S3 SSE-KMS, 버킷 퍼블릭 액세스 차단 |
| 백업 | 암호화, 별도 계정/리전 복제 |
| 키 관리 | AWS KMS, 자동 로테이션, 용도별 키 분리 |

### 4.2 인증

| 항목 | 설계 |
|---|---|
| 비밀번호 | Argon2id, 최소 길이 정책, 유출 비밀번호 차단(HIBP 등) |
| 2FA | 관리자 계정 **필수**, 일반 사용자 선택 |
| 세션 | Access 15분 + Refresh 14일 회전, 이상 감지 시 전체 무효화 |
| SSO | SAML 2.0 / OIDC (대형 고객) |
| 기기 바인딩 | 모바일 1인 1기기 원칙 ([06 §3.4](06-mobile-attendance.md#34-기기-바인딩)) |
| 계정 잠금 | 연속 실패 시 지수 백오프 |

### 4.3 테넌트 격리

```sql
ALTER TABLE <모든 테넌트 테이블> ENABLE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON <table>
  USING (tenant_id = current_setting('app.tenant_id')::uuid);
```

- 애플리케이션 필터링만 믿지 않습니다. **DB 레벨에서 강제**합니다.
- 테넌트 격리 위반을 탐지하는 자동 테스트를 CI에 포함합니다.

```typescript
// CI에서 실행: 다른 테넌트 데이터가 조회되면 실패
it('테넌트 A의 세션으로 테넌트 B 데이터를 조회할 수 없다', async () => {
  await setTenant(tenantA);
  const result = await db.query('SELECT * FROM member WHERE id = $1', [memberOfB]);
  expect(result.rows).toHaveLength(0);
});
```

### 4.4 애플리케이션 보안

| 위협 | 대응 |
|---|---|
| SQL Injection | ORM/파라미터 바인딩, 동적 쿼리 금지 |
| XSS | 출력 이스케이프, CSP 헤더 |
| CSRF | SameSite 쿠키 + CSRF 토큰 |
| IDOR | 모든 리소스 접근 시 스코프 검증 (RLS가 2차 방어) |
| 파일 업로드 | 확장자·MIME 검증, 별도 도메인 서빙, 바이러스 스캔 |
| 의존성 취약점 | Dependabot, `npm audit` CI 게이트 |
| 시크릿 유출 | git-secrets, AWS Secrets Manager, 코드 내 하드코딩 금지 |

### 4.5 인프라

- VPC 프라이빗 서브넷에 DB·AI 서비스 배치. 인터넷 직접 노출 없음.
- WAF (OWASP Top 10 룰셋) + Shield.
- 보안 그룹 최소 권한. 관리 접근은 SSM Session Manager (SSH 포트 미개방).
- CloudTrail, GuardDuty, Config 활성화.
- IaC(Terraform) + `tfsec`/`checkov` CI 검사.

## 5. ISMS-P 대응

병원 고객, 특히 중대형 병원은 도입 심사 시 정보보호 인증을 요구합니다.

### 5.1 준비 항목

| 영역 | 필요 산출물 |
|---|---|
| 관리체계 | 정보보호 정책, 조직도, 책임자 지정 |
| 위험관리 | 자산 목록, 위험 평가서, 이행 계획 |
| 접근통제 | 계정 관리 절차, 권한 검토 기록(반기) |
| 암호화 | 암호정책, 키 관리 절차 |
| 개발보안 | 시큐어 코딩 가이드, 코드 리뷰 기록 |
| 운영보안 | 변경관리, 로그 관리, 백업·복구 절차 |
| 침해대응 | 사고 대응 절차, 모의훈련 기록 |
| 개인정보 | 처리방침, 수집·이용 동의서, 파기 기록, 영향평가 |

### 5.2 현실적 계획

**인증 취득은 시간과 비용이 큽니다.** 1차 타겟(중소 병·의원)은 대부분 인증을 요구하지 않으므로, 다음 순서로 접근합니다.

```
Phase 1 : ISMS-P 통제 항목에 부합하는 설계·운영 (인증 미취득)
          → 보안 백서로 고객 실사 대응
Phase 2 : 중대형 병원 진입 시점에 인증 준비 착수
Phase 3 : 인증 취득
```

**중요: 나중에 인증을 받으려면 지금부터 기록을 남겨야 합니다.** 권한 검토, 변경 관리, 백업 테스트 같은 것들은 사후에 만들 수 없습니다. Phase 1부터 절차와 기록을 운영합니다.

## 6. 위탁 및 제3자 제공

### 6.1 우리가 수탁자인 관계

```
병원 (개인정보처리자)  →  위탁  →  MediWork (수탁자)
```

- **위탁 계약서(개인정보 처리 위탁 계약)** 를 표준 양식으로 준비합니다.
- 병원은 우리를 처리방침에 수탁자로 공개해야 합니다. 안내 자료를 제공합니다.
- 우리는 병원의 감독을 받아야 하므로, **고객이 요구할 수 있는 점검 항목**(접근 이력, 보안 조치 현황)을 제공하는 화면을 만듭니다.

### 6.2 재위탁 (클라우드, AI)

| 재수탁자 | 용도 | 고지 필요 |
|---|---|---|
| AWS (서울) | 인프라 | ○ |
| Anthropic (Claude API) | AI 기능 | ○ ⚖️ **국외 이전 검토 필요** |
| 알림톡 발송 대행 | 알림 | ○ |

**AI 관련이 가장 주의할 지점입니다.**

```
⚖️ 검토 필요 사항
 1. Claude API 호출이 개인정보 국외 이전에 해당하는지
 2. 해당한다면 필요한 고지·동의 절차
 3. 국외 이전 없이 목적을 달성할 수 있는 설계가 가능한지

→ 설계상 대응: 익명 ID 치환 ([08 §9.4](08-ai-features.md#94-데이터-취급))
   "김수진" → "M014" 로 치환해 전송하면 개인정보 전송 자체가 발생하지 않음.
   이 구조를 기본값으로 하면 논쟁의 상당 부분을 회피할 수 있음.
```

## 8. 침해 사고 대응

### 8.1 절차

```
탐지 → 초동 대응 → 영향 분석 → 통지 → 복구 → 사후 조치

⚖️ 개인정보 유출 시 법정 통지·신고 의무가 있습니다.
   통지 대상, 기한, 신고 기관, 통지 항목을 사전에 확인하고
   대응 매뉴얼과 템플릿을 준비해 두어야 합니다.
   사고 발생 후에 알아보면 늦습니다.
```

### 8.2 사전 준비

- 사고 대응 조직과 연락 체계 (24시간)
- 통지문·신고서 템플릿
- 로그 보존 (사고 원인 분석에 필수)
- 연 1회 이상 모의훈련
- 고객사 통지 채널 (상태 페이지, 담당자 직접 연락)

### 8.3 백업·복구

| 항목 | 목표 |
|---|---|
| RPO (데이터 손실 허용) | 5분 |
| RTO (복구 목표 시간) | 15분 |
| 백업 주기 | 자동 스냅샷 일 1회 + PITR |
| 백업 보관 | 35일 |
| 복구 훈련 | 분기 1회, 실제 복원 테스트 |

**복구 훈련을 실제로 해야 합니다.** 백업이 있는 것과 복구되는 것은 다릅니다.

## 9. 개발 프로세스 보안

| 단계 | 조치 |
|---|---|
| 설계 | 개인정보 영향평가 체크리스트 (신규 데이터 수집 시) |
| 코딩 | 시큐어 코딩 가이드, 민감 데이터 로깅 금지 규칙 |
| 리뷰 | 개인정보 취급 변경 시 보안 담당 리뷰 필수 |
| 테스트 | 테넌트 격리 테스트, 권한 우회 테스트 자동화 |
| CI | 시크릿 스캔, 의존성 취약점, IaC 스캔 |
| 배포 | 승인 게이트, 롤백 절차 |
| 운영 | 운영 DB 직접 접근 금지 (조회 도구 경유, 이력 기록) |

**"운영 DB 직접 접근 금지"가 실무에서 가장 안 지켜집니다.** 개발자가 psql로 붙어서 고객 데이터를 보는 상황을 원천 차단하려면, 승인 기반 조회 도구를 초기부터 만들어야 합니다.
