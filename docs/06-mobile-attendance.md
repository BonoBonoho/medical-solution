# 06. 모바일 출퇴근 기록

## 1. 설계 목표와 긴장 관계

이 기능에는 서로 충돌하는 세 가지 요구가 있습니다.

```
   정확성 (부정 출근 방지)
        ↕ 충돌
   편의성 (교대 시각에 수십 명이 3초 안에)
        ↕ 충돌
   프라이버시 (직원 위치를 상시 추적하지 않음)
```

**우선순위 결정: 편의성 > 프라이버시 > 정확성.**

이유는 이렇습니다. 정확성을 최우선에 두면 검증이 엄격해지고, 그러면 정상 출근인데 실패하는 경우가 늘어납니다. 실패한 직원은 관리자에게 가서 수동 입력을 요청하고, 그게 반복되면 병동 전체가 "그냥 수기로 하자"로 돌아갑니다. **시스템 밖으로 나간 기록은 0의 정확성**을 가집니다.

부정 출근은 완벽히 막을 수 없습니다. 대신 **탐지 가능하게** 만들고 이상 패턴을 관리자에게 보여주는 쪽이 현실적입니다.

## 2. 위치 검증 방식 비교

| 방식 | 정확도 | 실내 | 위조 난이도 | 배터리 | 비용 |
|---|---|---|---|---|---|
| **WiFi BSSID** | 높음 (AP 반경) | ◎ | 높음 | 낮음 | 없음 |
| **GPS 지오펜스** | 중간 (5~50m) | △ 열악 | **낮음** (Mock 앱 다수) | 중간 | 없음 |
| **BLE 비콘** | 높음 (1~10m) | ◎ | 중간 | 중간 | 비콘 구매·관리 |
| **NFC 태그** | 매우 높음 | ◎ | 높음 | 없음 | 태그 저렴 |
| **사업장 IP** | 낮음 (건물 단위) | ◎ | 중간 (VPN) | 없음 | 없음 |

### 2.1 채택: WiFi 우선, GPS 보조

**병원 실내에서 GPS는 신뢰할 수 없습니다.** 지하 검사실, 중환자실, 콘크리트 건물 내부에서 정확도가 100m를 넘거나 아예 안 잡힙니다. 반면 병원은 예외 없이 WiFi AP가 촘촘히 깔려 있습니다.

```
검증 순서
 ①  WiFi BSSID 매칭 (스캔된 BSSID 중 하나라도 화이트리스트에 있는가)
       → 성공 시 confidence = HIGH, 종료
 ②  GPS 지오펜스 (반경 내인가 + Mock 아님 + 정확도 임계값 이하)
       → 성공 시 confidence = MEDIUM, 종료
 ③  BLE 비콘 (설치된 경우)
       → 성공 시 confidence = HIGH, 종료
 ④  모두 실패
       → 기록 저장 + verification = PENDING_REVIEW
```

**BSSID를 쓰는 이유 (SSID가 아니라)**: SSID는 이름일 뿐이라 아무나 같은 이름의 핫스팟을 만들 수 있습니다. BSSID는 AP의 MAC 주소로, 위조하려면 MAC 스푸핑이 가능한 장비와 지식이 필요합니다. 완벽하진 않지만 난이도가 크게 다릅니다.

### 2.2 플랫폼별 WiFi 접근 제약

여기서 실무적으로 막히는 지점이 있습니다.

**iOS**
- 주변 AP 목록 스캔 API는 일반 앱에 **제공되지 않습니다.**
- 현재 연결된 네트워크 정보만 `NEHotspotNetwork.fetchCurrent(completionHandler:)` 로 조회 가능하며, 이를 위해 **Access WiFi Information** Entitlement가 필요합니다.
- 즉 iOS에서는 **"병원 WiFi에 연결되어 있는가"** 만 확인할 수 있고, "근처에 병원 AP가 보이는가"는 확인할 수 없습니다.
- ⚠️ 정확한 API 가용성과 Entitlement 요건은 **현행 iOS SDK 문서를 반드시 확인**해야 합니다. Apple의 프라이버시 정책 변경이 잦은 영역입니다.

**Android**
- `WifiManager.getScanResults()` 로 주변 AP 스캔이 가능하나, **위치 권한이 필요**하고 스캔 쓰로틀링이 적용됩니다.
- Android 버전에 따라 요구 권한과 쓰로틀 정책이 다릅니다. (`ACCESS_FINE_LOCATION`, `NEARBY_WIFI_DEVICES` 등)
- ⚠️ 대상 API 레벨별 요건 확인 필수.

**설계 대응**

이 비대칭성 때문에 검증 로직을 플랫폼별로 분기합니다.

```
iOS   : 연결된 네트워크의 BSSID 1개 → 화이트리스트 대조
        (병원 WiFi 미연결 시 GPS로 폴백)
Android: 스캔된 BSSID N개 → 하나라도 매칭되면 성공
        (연결 여부 무관 — 더 관대하고 편리)
```

**따라서 도입 시 "병원 WiFi에 연결해 두세요"라는 온보딩 안내가 iOS 사용자에게 필요합니다.** 이걸 제품 설계에서 놓치면 iOS 사용자만 계속 실패합니다.

## 3. 위·변조 방지

### 3.1 위협 모델

| 위협 | 수법 | 대응 |
|---|---|---|
| 대리 출근 | 동료에게 계정 공유 | 기기 바인딩 (1인 1기기) |
| 위치 조작 | Mock location 앱 | `isFromMockProvider` 검사 + 무결성 검증 |
| 앱 변조 | 리패키징, 후킹 | Play Integrity / App Attest |
| 시각 조작 | 기기 시계 변경 | 서버 시각 대조, 이탈 시 PENDING |
| 오프라인 큐 조작 | 로컬 DB 직접 수정 | 기기 키 서명 + 시퀀스 번호 |
| 자동화 | 스크립트로 정시 기록 | 기기 무결성 + 패턴 이상탐지 |

### 3.2 기기 무결성 검증

```
Android: Play Integrity API
  → MEETS_DEVICE_INTEGRITY 미충족 시 confidence 강등 (거부 아님)
iOS:     DeviceCheck / App Attest
  → Attestation 실패 시 confidence 강등
```

**실패해도 거부하지 않고 강등하는 이유**: 커스텀 ROM을 쓰는 개발자, 오래된 기기, 일시적 서비스 장애로 무결성 검증이 실패할 수 있습니다. 이런 사람들의 출근을 막으면 안 됩니다. `PENDING_REVIEW`로 보내 관리자가 판단하게 합니다.

⚠️ Play Integrity와 App Attest는 API 요건과 응답 형식이 변경되어 왔습니다. 구현 전 **현행 공식 문서 확인**이 필요합니다.

### 3.3 Mock Location 탐지

```kotlin
// Android
val isMock = location.isMock  // API 31+
             || location.isFromMockProvider  // deprecated, 하위 호환

// 추가 신호
// - 개발자 옵션의 모의 위치 앱 설정 여부
// - GPS 좌표의 부자연스러운 정밀도 (소수점 이하가 지나치게 깔끔)
// - 이동 속도 이상 (직전 기록 위치에서 물리적으로 불가능한 이동)
```

**이동 속도 검사가 실용적으로 유용합니다.** 직전 기록이 30분 전 서울이고 지금 부산이면 명백한 이상입니다. 이건 앱 조작 여부와 무관하게 서버에서 판정 가능합니다.

### 3.4 기기 바인딩

```
최초 로그인 → 기기 등록 요청 → 관리자 승인 → ACTIVE
기기 변경   → 기존 기기 REVOKE + 신규 등록 → 관리자 승인
```

- 기본 정책: **1인 1기기**. 태블릿 병행 사용이 필요하면 관리자가 예외 허용.
- 기기 변경 요청이 잦은 사용자는 대시보드에 표시. (기종 변경은 실제로 흔하므로 차단이 아니라 가시화)

## 4. 오프라인 처리

### 4.1 로컬 큐 설계

```
체크인 버튼 탭
  │
  ├─ 로컬 SQLite에 즉시 저장 (status: QUEUED)
  │    { seq, type, capturedAt, location, signature }
  │    signature = Sign(devicePrivateKey, seq || type || capturedAt || locationHash)
  │
  ├─ UI: "기록 대기중" 표시 (⚠️ "완료" 아님)
  │
  └─ 전송 시도
       ├─ 성공 → status: SYNCED, UI "기록 완료 ✓"
       └─ 실패 → 백오프 재시도 (30s, 2m, 10m, 30m, 1h)
                 + 앱 포그라운드 진입 시 즉시 재시도
                 + 네트워크 복구 감지 시 즉시 재시도
```

### 4.2 서명과 시퀀스

기기 키페어를 등록 시 생성하고, 공개키를 서버에 저장합니다. 오프라인 기록은 개인키로 서명합니다.

- **목적**: 로컬 DB를 루팅해 직접 수정한 기록을 걸러냅니다. 서명이 안 맞으면 `PENDING_REVIEW`.
- **시퀀스 번호**: 단조 증가. 서버가 `1, 2, 4`를 받으면 3번이 누락(또는 삭제)되었음을 압니다.

### 4.3 UI 원칙 — 가장 중요한 부분

```
❌  체크인 → "출근 완료!"  (실제로는 큐에만 들어감)
✅  체크인 → "기록 대기중 · 네트워크 연결 시 자동 전송됩니다"
             → 동기화 완료 후 → "출근 완료 ✓ 07:02"
```

**"기록됨"과 "전송됨"을 구분하지 않으면 나중에 반드시 분쟁이 납니다.** 직원은 기록했다고 믿었는데 서버에 없는 상황이 생기고, 그때는 누구도 증명할 수 없습니다.

홈 화면 상단에 대기 건수를 항상 표시합니다.

```
┌────────────────────────────────────┐
│ ⚠ 전송 대기중인 기록 2건            │
│   네트워크 연결 시 자동 전송됩니다   │
└────────────────────────────────────┘
```

### 4.4 지연 도착 처리

```
received_at - captured_at > 4시간  →  PENDING_REVIEW
```

며칠 뒤에 도착한 기록은 조작 가능성을 배제할 수 없습니다. 자동 승인하지 않고 관리자 확인을 거칩니다.

## 6. 권한 요청 전략

권한 거부는 기능 실패로 직결되므로 요청 시점과 문구가 중요합니다.

```
① 온보딩에서 설명 (권한 요청 전)
   "출퇴근 기록 시 병원에 계신지 확인하기 위해 위치 정보가 필요합니다.
    ▸ 출퇴근 버튼을 누르는 순간에만 확인합니다
    ▸ 평소 위치는 수집하지 않습니다
    ▸ 위치 이력은 저장되지 않습니다"

② 첫 체크인 시도 시 시스템 권한 요청
   → "앱 사용 중에만 허용"으로 충분. '항상 허용' 요구하지 않음.

③ 거부한 경우
   → 대체 경로 안내 (병동 키오스크, 웹, 승인 요청)
   → 설정에서 다시 켜는 방법 안내
   → ⚠️ 반복적인 권한 재요청 팝업 금지. 사용자를 괴롭히면 앱을 지웁니다.
```

**'항상 허용(Always)' 권한을 요구하지 않는 것이 중요합니다.** 백그라운드 위치 권한은 앱스토어 심사에서도 강한 정당화를 요구하고, 직원의 거부감도 큽니다. 체크인 순간의 전경 위치만으로 목적을 달성할 수 있습니다.

## 7. 대체 기록 수단

모바일이 안 되는 상황을 위해 항상 대안이 있어야 합니다.

| 수단 | 상황 | 검증 |
|---|---|---|
| 병동 키오스크(태블릿) | 개인 휴대폰 미소지·권한 거부 | 사번 + PIN, 기기 자체가 고정 위치 |
| 웹 체크인 | PC 상주 직군(원무·행정) | 사업장 IP 대역 |
| 관리자 대리 입력 | 앱·키오스크 모두 불가 | 사유 필수, 감사 로그 |
| NFC 태그 | 향후 | 태그 UID 검증 |

**개인 휴대폰을 업무에 쓰도록 강제할 수 없다는 점**을 고려해야 합니다. 회사가 기기를 지급하지 않는 이상, 개인 폰 사용을 거부하는 직원에게 불이익을 주는 구조는 노무 리스크가 됩니다. 키오스크 대안이 반드시 필요합니다.

## 8. 이상 탐지 신호

수집된 증거로 서버에서 판정합니다. **자동 징계가 아니라 관리자에게 보여주는 것**이 목적입니다.

| 신호 | 판정 기준 |
|---|---|
| 물리적 불가능 이동 | 직전 기록 위치 대비 이동 속도가 비현실적 |
| 동일 기기 다중 계정 | 같은 device_fingerprint로 여러 member가 기록 |
| 동일 좌표 반복 | GPS 좌표가 소수점까지 완전히 동일하게 반복 (Mock 의심) |
| 근무 없는 날 기록 | 근무표에 배정이 없는데 체크인 |
| 정시 정각 패턴 | 매일 정확히 07:00:00에 기록 (자동화 의심) |
| 오프라인 큐 편중 | 특정인만 오프라인 기록 비율이 지나치게 높음 |
| 시퀀스 누락 | 오프라인 시퀀스 번호에 빈 구간 |

**중요**: 이 신호들은 **의심일 뿐 증거가 아닙니다.** UI에서 "부정 출근"이라고 단정하는 표현을 쓰면 안 됩니다. "확인이 필요한 기록"으로 표현하고, 관리자가 당사자에게 확인하는 흐름을 만듭니다. 알고리즘이 사람을 단정하게 만들면 제품이 노무 분쟁의 도구가 됩니다.

## 9. 개인정보 처리

| 항목 | 수집 시점 | 보관 | 목적 |
|---|---|---|---|
| GPS 좌표 | 체크인/아웃 시점만 | 90일 | 위치 검증, 분쟁 대응 |
| WiFi BSSID | 체크인/아웃 시점만 | 90일 | 위치 검증 |
| 기기 식별자 | 기기 등록 시 | 기기 해제까지 | 바인딩 |
| 무결성 토큰 | 검증 후 즉시 폐기 | 미보관 | — |

- **90일 후 원시 좌표는 삭제**하고 검증 결과(`VERIFIED`/`method`/`confidence`)만 남깁니다. 근태 기록 자체는 법정 보존기간(3년) 유지하되, 위치 원본은 필요 이상 보관하지 않습니다.
- 상세 법적 근거와 동의 절차는 [10. 보안·규제 준수](10-security-compliance.md) 참고.
- ⚖️ **검토필요**: 위치정보 수집·이용이 「위치정보의 보호 및 이용 등에 관한 법률」상 **위치기반서비스사업 신고 대상**인지 여부를 반드시 확인해야 합니다. 개인위치정보를 다루는 서비스는 신고 의무가 발생할 수 있으며, 이는 서비스 출시 전 처리해야 할 사항입니다.
