# @mediwork/ai

근무표 자동 생성. Python + FastAPI + OR-Tools CP-SAT.

수간호사가 매월 2~5일을 쓰는 작업을 수 분으로 줄이는 것이 목표다.

## 실행

```bash
pip install -e '.[dev]'
python3 -m uvicorn mediwork_ai.main:app --port 3002 --app-dir src
```

| 환경변수 | 설명 |
|---|---|
| `EXPOSE_DOCS=1` | `/docs`를 켠다. 기본은 꺼져 있다 |
| `ANTHROPIC_API_KEY` | 자연어 제약 해석에만 필요. 없어도 생성은 동작한다 |

**이 서비스는 VPC 내부에서만 접근 가능해야 한다.** 입력에 구성원 이름과
휴가 일정이 들어 있고, 인터넷에 노출할 이유가 없다.

## 왜 LLM이 아니라 CP-SAT인가

근무표 생성은 "그럴듯한 답"이 아니라 **제약을 만족하는 답**이 필요하다.
법정 근로시간을 어긴 근무표는 아무리 보기 좋아도 쓸모가 없고, 근로감독에서
"AI가 만들었습니다"는 변명이 되지 않는다.

CP-SAT는 결정론적이고, 제약 만족을 보장하며, 왜 해가 없는지 물어볼 수 있다.
LLM은 이 셋 중 어느 것도 못 한다. 대신 LLM은 **자연어 요청을 구조화 제약으로
바꾸는 일**을 맡는다 — 그건 LLM이 잘하고 CP-SAT는 못 하는 일이다.

```
자연어 요청 ──[Claude]──→ 구조화 제약 ──[결정론적 검증]──→ CP-SAT ──→ 근무표
                             ↑                                        │
                     여기가 실제 방어선                      [독립 재검증] ─┘
```

## 세 겹의 안전장치

### 1. 하드 제약은 타협하지 않는다

법정 제약을 소프트로 내리면 "거의 맞는" 근무표가 나온다. 만족할 수 없으면
근무표를 내지 않고 **무엇이 충돌하는지** 말한다.

해가 없으면 제약군을 하나씩 빼고 다시 풀어, 빼니까 풀리는 제약을 지목한다.

```json
{
  "status": "INFEASIBLE",
  "conflicts": [
    { "constraint": "demand",
      "detail": "최소 인력 제약을 빼면 근무표가 만들어집니다. 이 제약이 다른 조건과 충돌합니다." }
  ]
}
```

`INFEASIBLE`만 던지면 관리자는 무엇을 고쳐야 할지 알 수 없다.

### 2. 못 지킨 요청은 반드시 보고한다

희망휴무 4건 중 1건을 못 지켰으면 그 1건을 **이름과 날짜와 이유로** 말한다.

```json
{ "member_id": "m1", "work_date": "2026-08-05", "kind": "PREFERRED_OFF",
  "reason": "8/5 최소 인력을 채우려면 간호사1의 근무가 필요해 희망휴무를 반영하지 못했습니다 (배정: D)." }
```

조용히 무시하면 관리자는 다음 달부터 시스템 밖에서 일한다.

### 3. 결과를 독립적으로 재검증한다

CP-SAT는 자신이 받은 제약을 어기지 않는다. 하지만 **모델을 잘못 짜는 것**은
언제든 가능하다 — 슬라이딩 윈도우 범위를 하나 잘못 잡거나, 경계 조건을
빠뜨리거나.

`verify.py`가 배정 결과를 직접 훑어 같은 제약을 다시 확인한다. 솔버는 변수와
선형식으로, 검증기는 결과를 순회하는 방식으로 — 일부러 다른 방법을 썼다.
같은 실수를 두 번 하기 어렵게 만드는 것이 목적이다.

검증에 걸리면 결과를 폐기하고 500을 낸다. **잘못된 근무표를 200으로
돌려주면 그대로 확정돼 근로감독까지 간다.**

## 자연어 제약 해석

LLM은 사람 이름을 잘못 짚고, 없는 근무유형을 만들어내고, 요청에 없는 제약을
추가한다. 그래서 해석 결과는 그대로 쓰지 않는다.

| 단계 | 하는 일 | LLM 필요 | 테스트됨 |
|---|---|---|---|
| `parse_constraints()` | 자연어 → 구조 | ✅ | ❌ **미검증** |
| `validate_parsed()` | 명단·근무유형·기간 대조, 확신도 확인 | ❌ | ✅ |
| `apply_constraints()` | 검증 통과분만 요청에 반영 | ❌ | ✅ |

확신도가 `0.8` 미만이면 자동 반영하지 않고 사용자 확인을 요청한다.
해석하지 못한 요청(`UNKNOWN`)도 조용히 버리지 않고 되묻는다 — 버리면
관리자는 반영된 줄 안다.

> ⚠️ **`parse_constraints()`는 실제 API에 대해 검증되지 않았다.** 이 저장소에
> API 키가 없어 호출해 본 적이 없다. 형태만 맞춰 두었으므로 사용 전 실제
> 응답으로 반드시 확인할 것. 나머지 두 단계는 LLM 없이 동작하고 테스트로
> 고정되어 있다 — LLM이 무엇을 뱉든 그 둘을 통과하지 못하면 근무표에
> 영향을 주지 못한다.

## API

### `POST /api/v1/roster/solve`

해가 없어도 **200**이다. 4xx로 던지면 클라이언트가 "요청이 잘못됐다"고
해석하지만, 실제로는 요청이 옳고 조건이 서로 모순인 것이므로 구분해야 한다.

| 상태 | 의미 |
|---|---|
| `OPTIMAL` | 타임박스 안에 최적해를 찾음 |
| `FEASIBLE` | 제약을 만족하는 해를 찾음. 최적은 아닐 수 있음 |
| `INFEASIBLE` | 조건이 모순. `conflicts`에 원인 |
| `UNKNOWN` | 타임박스 안에 아무 해도 못 찾음. 시간을 늘리거나 조건을 완화 |

`random_seed`를 주면 워커를 1개로 줄여 **같은 입력에 같은 근무표**가 나온다.
재현 불가능한 생성기는 "어제 만든 근무표가 왜 다르지"를 설명할 수 없다.

## 테스트

```bash
python3 -m pytest -q     # 51개
```

확인하는 것은 "그럴듯한 근무표가 나오는가"가 아니라 **하드 제약이 실제로
지켜지는가**다. 생성 결과를 직접 훑어 금지 패턴·연속 야간·최소 휴식·주당
휴무일·최소 인력을 하나하나 검사한다. 검증기 자체도 일부러 위반을 심어
잡아내는지 확인한다.

## 알려진 한계

- **연속 야간 경계 계산.** 직전 기간의 마지막 하루만 받으므로, 직전 기간
  끝에서 이미 야간이 이어지고 있었다면 최대 1일까지 과소 계산될 수 있다.
  직전 기간 전체를 받도록 입력을 넓혀야 한다.
- **부분 주는 주 단위 제약을 적용하지 않는다.** 기간 경계에 3일만 걸린 주에
  "52시간을 넘지 않았다"고 말하는 것은 무의미하기 때문이다. 대신 그 주가
  실제로는 초과일 수 있다는 뜻이므로, 근무표를 주 경계에 맞춰 끊는 것이 낫다.
- **가중치 기본값은 출발점일 뿐이다.** 중환자실과 외래는 우선순위가 완전히
  다르다. 병동별 설정으로 빼기 전까지 이 숫자는 어느 병동에도 맞지 않는다.
- **프리셉터 페어링·연차 소진 유도 미구현.** 설계 문서에는 있으나 실제 병동의
  페어링 규칙을 관찰하지 않고 만들면 틀린다.
- 코어 API와의 연동(컨텍스트 수집 → 생성 → 결과 반영)은 아직 없다.
  지금은 요청에 모든 입력을 직접 담아 보낸다.
